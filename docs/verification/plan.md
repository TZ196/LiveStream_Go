| BASE-04 | 启动 MySQL 并应用 users 迁移；检查密码缺失/错误、不可达、缺少迁移/列、版本不符；运行中停止及恢复数据库 | 初始化失败不监听 HTTP；正常 readyz 为 200，数据库故障时为 503 且 healthz 仍为 200，恢复后重新就绪；用户名唯一及格式约束有效；迁移入口见 [部署说明](../deployment.md#启动-mysql-和后端) |
| AUTH-01 | 注册、大小写用户名冲突、正确及错误密码登录 | 唯一约束生效；密码哈希不明文；正确返回期限，错误不泄露账户详情 |
| AUTH-02 | 无令牌、错误算法、签名、aud/iss、过期及越权输入 | 401/403，不能改变他人数据，日志无凭据 |
| AUTH-03 | 注册/登录每 IP 连续尝试、伪造转发头、并发密码计算、数据库无响应、服务重启 | 超限 429 和 Retry-After；身份来自验签结果；数据库失败 503，恢复后可继续；重启不丢账号，不输出密码或令牌 |
| AUTH-04 | 浏览器登录、刷新/重开页面、退出及多标签页；检查过期、损坏存储、401、503、网络中断与恢复 | 实际身份来自 users/me；刷新不退出且不延长原有效期；退出/过期清理凭证；同源标签页同步，恢复失败可重试，迟到响应不能恢复已退出会话；注册无自动重发 |
| ROOM-01 | 创建、列表翻页、详情、无效游标 | 所有者来自身份；分页稳定；无重复或跨过滤条件游标混用 |
| ROOM-02 | 非房主开关播、同方向重复操作、并发开关播；后续检查关闭与发送并发 | 越权失败；重开保留 id/title/created_at 并清空 closed_at；同轮重复关闭时间不变，下轮重新记录；交错请求各返回本次操作状态；实时准入边界符合领域规则 |
| ROOM-03 | 同账号两个页面、重复清理、断网、进程重启 | 在线数 2→1→0，无负数；重启后按重连重新统计 |
| ROOM-05 | 同一房间开播、结束并重新开播；并发重试及旧场点赞迟到 | 每轮唯一 session_id；同向重试不新建场次；两个场次点赞分别计数；旧事件不计入新场；房间和场次状态事务一致；数据库拒绝 room_id 与 session_id 不匹配的事件；旧数据不伪造历史 |

P2 另执行 ROOM-04：真实浏览器登录、创建防重复提交、列表筛选及加载更多、详情、房主结束后重新开播和非房主操作边界；模拟创建响应丢失时提示先查询本人房间，开关播结果未知时先刷新详情，不自动重发。检查卸载取消、401 退出和窄屏显示。ROOM-02 的关闭与发送并发部分、ROOM-03 仍按 [待解决问题](../status.md#待解决问题)留待实时阶段。

GORM 接入后，BASE-04 需复查查询错误不会污染共享实例、探针恢复正常，以及数据库无响应时初始化可超时或被退出信号取消；ENV-03 同时确认启动未调用 AutoMigrate、users 及迁移文件保持。GORM 是查询工具，不能用仅连接成功代替真实故障与数据保留检查。

## 实时连接与前端

| 案例 | 操作 | 必须观察到的结果 |
| --- | --- | --- |
| WS-01 | 合法票据、过期票据、两连接并发使用同票据 | 合法升级；过期拒绝；同票据最多一次成功 |
| WS-02 | 错误 Origin、票据跨房间、JWT 到期 | 升级前拒绝；已连接到期关闭并要求认证 |
| WS-03 | 两个房间、多用户发弹幕，广播早于 ACK；并发分发时核对同房间消息顺序 | 本房间可见、跨房间不可见；前端同事件只有一项；P3 核对分发入队顺序，P5 起对照同房间弹幕 Kafka 日志顺序核对已交付的唯一弹幕事件，不以浏览器墙钟作为全序 |
| WS-04 | 停止读取的慢客户端、超大帧、超过队列或连接容量 | 慢连接退出；其他连接继续；内存、goroutine 和队列有界 |
| WS-05 | P3 用可控发布器模拟阻塞、队列满和取消；P4 起对点赞注入实际中间件迟缓，P5 覆盖弹幕，同时断开已有连接并尝试加入 | 清理不等待外部发布；新准入按当前能力及时成功或明确拒绝；等待任务与队列有界，取消和退出按预算回收。记录故障期间及恢复后的任务、队列与连接数 |
| UI-01 | 断网、重连、主动离开、卸载组件、令牌过期 | 退避有上限；主动离开不重连；无残留定时器与重复连接 |
| UI-02 | 老版本 LIKE_UPDATE、旧 epoch、历史与实时重叠；P4 同时存在 memory 弹幕和 Kafka 点赞 | 计数不被旧状态覆盖，epoch 变更重新取快照，event_id 去重；delivery_modes 按类型分别报告，不能把两条链路描述为同一种模式 |
| COUNT-01 | 连续不同 ID 点赞、同 ID 并发重试、跨固定窗口限流；点赞后立即退出至房间无人，以及 Redis 暂不可用 | 新操作各加一；重试不多算；房间无人不丢已接受动作；限制符合固定窗口定义。故障按阶段接受及恢复边界处理，不靠内存批次静默补数，也不把不可用计数显示为零 |

## 幂等及 Kafka

| 案例 | 故障或操作 | 必须观察到的结果 |
| --- | --- | --- |
| IDEM-01 | 同一用户的 request_id、相同内容并发重试 100 次；覆盖确认丢失及发送者重启 | 一个稳定 event_id 与首次消息内容；LIKE 只增加一次；MySQL 唯一索引约束同一事件，最终业务记录一条；未知状态不得伪称成功或失败 |
| IDEM-02 | 同一用户 request_id 并发变更房间、场次、类型或内容，及点赞试图传入 count | 非法 count 在发布前拒绝；不同内容可能都进入 Kafka，消费者发现相同 event_id 指纹冲突后暂停分区并告警；覆盖不同房间跨分区、两组可能先见不同版本的情况 |
| IDEM-03 | Broker 接受后丢弃 ACK，或应用在发送后退出 | 不向用户展示 Kafka 内部确认丢失；不伪报成功或确定失败；有界重试原 ID、时间、场次和内容，计数与历史不重复 |
| IDEM-04 | 窗口边界、未来 5 分钟之外、24 小时请求窗口后重试 | 不因新键或换时间解释旧 ID 而重新产生业务效果；无法查询的历史结果不标为确定失败 |
| KAFKA-01 | 一条事件被两个消费组读取，Worker 停止后重启 | 两条职责独立；广播不分走持久化消息；Worker 续消费 |
| KAFKA-02 | P4 起在数据库事务前、事务后 Kafka 提交前分别终止 Worker | 未提交事务不推进；已提交事务重读不重复业务写入 |
| KAFKA-03 | P4 起分别让 Redis 和 MySQL 不可用并恢复，观测两个消费组 | Redis 失败时不推进实时 offset，MySQL 组可在 Kafka/MySQL 可用时继续；MySQL 失败时不推进持久化 offset，恢复后重试且计数、落库不重复；有界重试后暂停，不把正常消息送入死信 |
| KAFKA-04 | 插入未知版本/坏记录，并模拟隔离存储失败及分区撤销 | 隔离未落库不提交；成功后保留原文；旧分区任务退出后交接 |
| KAFKA-05 | P4 起分别对实时消费者和 Worker 连续触发多轮分区撤销、重新分配及退出；P4 覆盖低流量时间触发、满批次和未完成批次 | 新会话资源有效，无向已关闭通道发送或重复关闭；旧任务按预算退出，不越权推进检查点；未完成记录可重读且不重复业务效果，低流量记录不会无限等待凑批 |
| KAFKA-06 | 隔离 Topic 用 16 分区和实际 Producer，向同一房间发送至少 10000 个不同点赞事件，再测试多个房间、相同事件重试、弹幕及关闭并发 | 记录每分区 Broker ACK 数；单房间点赞覆盖 16 分区且每分区为平均值的 70%–130%；多个房间分别覆盖所有分区；相同事件重复 Key 与分区不变；校验消息 Key 与载荷及 murmur2 一致性；同房间弹幕保持分区与日志顺序，不要求点赞之间或点赞与弹幕的全序；P4 验证 Redis 原子去重计数、MySQL event_id 唯一约束、两组各自提交和检查点及关闭后的在途边界；P5 验证弹幕分区顺序。记录失败和环境，不把独立旧项目实验作为本契约的实测 |
| HIST-01 | 先广播后落库，多页历史并与实时列表合并 | 短暂滞后可解释；分页无无限返回；事件不重复展示 |

## 恢复验收

| 案例 | 操作 | 必须观察到的结果 |
| --- | --- | --- |
| REC-01 | 保持 Kafka/SQL，模拟 Redis 完全丢失 | 禁止按零继续；停写→屏障 B→Worker 追平→新 epoch；唯一点赞数与 SQL 一致，恢复后再点赞仅加一 |
| REC-02 | 恢复中断、Redis AOF 位置落后于 Kafka 提交、任意回退位移、8 天旧积压、Lua 错误 | 不暴露半完成投影；不在过期去重状态上继续计数；完整恢复后才开放写入 |
| REC-03 | 日志保留缺口、未解决隔离事件、数据库不可用、积压或资源保护阈值 | 保护阈值拒绝新准入；恢复条件不足时保持不可写，不声称零丢失或成功恢复 |

故障注入使用隔离的开发数据和明确的故障点。删除数据卷、破坏用户已有数据、重置真实消费位置不由普通测试授权覆盖。恢复用例应记录初始计数、唯一事件数、各分区屏障和检查点，不能只截图“服务启动成功”。

## 环境和性能

ENV-01 验证 WSL 内 Docker 客户端和服务端、Compose、数据库 Migration、依赖锁文件与启动说明；ENV-02 验证五服务启动、前端静态资源、HTTP 与 WS 代理、宿主/容器 Kafka 地址、持久卷重启后数据仍在。

ENV-03 从 P1b 起在隔离开发数据库写入已知业务数据，重复启动 API，核对数据与迁移版本；P2 增加房间数据，P4 起启动及重启 Worker，补充历史事件和检查点。正常启动不得删表或重建；只检查迁移版本，缺少所需迁移时按启动错误处理。此案例不授权清理用户现有数据库。

ENV-04 验证独立 GORM 迁移命令：空库按 1→2→3 执行，已有版本 1 补 2、3，已有版本 2 只补 3，已有版本 3 重复运行不改变成功时间和数据；与历史 SQL 对照字段、索引、字符集和约束行为。构造建表冲突、非法存量数据、成功记录写入失败，必须非零退出、不执行后续版本；DDL 已完成的部分不能伪称回滚。未知高版本、断号及缺列必须拒绝；同库持锁时第二个命令失败，结束或取消后释放资源。帮助无需密码，迁移不受 HTTP 参数影响；核对启动超时、取消和日志不包含秘密。所有破坏性样例仅在本次新建的临时数据库中运行，不能作用于用户现有库。

SEC-01 检查密码和票据脱敏、文本按纯文本显示、数据库参数绑定、原始错误不回显。OBS-01 将一次业务请求的 request_id、event_id、日志位移、数据库记录和结果串联，记录 UNKNOWN 与失败分类。

PERF-01 先测单房间，再测多房间及慢客户端，逐级提高负载；每轮记录 CPU、内存、Go/Node/中间件版本、连接数、消息大小、发送率、测试时长、成功率、ACK/广播/持久化延迟 p50/p95/p99、消费者积压和恢复时间。记录热身与稳态区间，不能用发送量替代成功广播或落库量。

每一档负载都同时核对唯一事件和点赞正确性，超过保护上限时验证拒绝是否可解释。先形成基线，再根据真实瓶颈优化，不预设十万连接等性能结论。

PERF-02 在使用压测工具得出性能结论前，先用已知规模的单房间和多房间输入，注入重复接收、延迟、漏收、连接退出及落库滞后，核对统计程序。预期接收集合按房间和事件定义；唯一业务接受、连接投递和唯一落库分开计数；停发后排空并在截止时间核对，在途或未决不直接算丢失。异步 Producer 入队完成和 Kafka 位移提交均不能替代数据库实际完成证据。

上述启动、会话、连接隔离及计量案例补充自 [参考项目审查](../reviews/live-stream-danmaku-review.md)。源码推导出的风险提供验收输入，新增案例仍待对应阶段实际执行。

## 指标口径与证据记录

从 P1a 开始保留各阶段的构建、联调和失败案例证据；具备对应链路后采集基础指标，P8 再进行完整负载与故障测量。每项指标标明“目标”“保护阈值”或“实测”，尚未测量时填“未测量”，不能填 0。时延或吞吐目标如需作为通过条件，先登记数值、适用负载及理由；探索性基线测试可不预设性能目标，但不能据此宣称满足未事先定义的性能要求。

| 指标 | 统一口径及需要记录的边界 |
| --- | --- |
| 负载 | 实际连接数、房间与用户分布、消息类型及字节数、每秒发送尝试数、唯一业务动作数；重试单独统计，负载输入不作为成功量 |
| 业务结果比例 | 以测量期首次发送的唯一逻辑动作数为分母，在核对截止时分别报告已确认接受、明确拒绝、未决的数量及比例；同一动作只归入一个最终类别，重试不扩大分母；接受比例不作为广播送达率或落库率 |
| 接受与落库吞吐 | 同一统计窗口内客户端首次确认接受的唯一事件数/秒、数据库实际新增的唯一业务事件数/秒分别记录；memory、redis、kafka 接受模式分开报告 |
| 接受延迟 | 从压测端首次发送该逻辑请求到首次收到接受 ACK，包含重试等待；拒绝、未决和超时另列，不能从成功率分母中删除；报告成功样本量及 p50/p95/p99 |
| 广播延迟与覆盖 | 从首次发送到接收端首次收到相同 event_id，按事件与接收连接对统计；试验预先定义接收集合，退出、被断开及未收到分别记录；成功接收延迟不能单独证明消息送达率 |
| 持久化可见延迟 | 从首次发送到观察器首次查到已提交业务记录；说明轮询间隔、采样方式和查询开销，此值不直接当作数据库事务执行耗时 |
| 正确性与失败分类 | 用测试输入的唯一业务动作、确认结果及故障后核对结果建立预期集合，比较实际事件和点赞增量；重复业务效果、冲突、拒绝、未决和隔离分开计数；无法核实的操作保留未决，不按成功或失败凑齐结果 |
| 消费积压 | 按消费组及分区记录日志末端 next_offset、已提交 next_offset 和两者差值，另记 Worker 数据库检查点及最早未持久化事件年龄；位移差不等于等待时间 |
| 资源与恢复 | 分别记录服务端和压测端 CPU、内存、goroutine、队列峰值及 Redis 内存；故障从注入到检测、停写、恢复的时间分别记录，恢复完成须同时满足开放写入和一致性断言；恢复失败也保留原因与耗时 |

延迟优先使用同一压测时钟的单调时间；多个进程或机器采样时记录时钟同步方式和误差，不能直接相减未校准的墙钟。固定统计窗口、预热和稳态时长，并设定排空与核对截止时间；截止后仍未知的请求继续列为未决。异常和失败样本的数量与观察期限需与成功样本一起报告。

每份实验记录包含：需求/案例编号与假设、代码提交或 PR、机器资源与软件版本、配置和数据规模、复现命令及故障点、预热/稳态时长与样本量、原始日志或数据位置、测量方法、结果和限制。优化前后采用相同业务保证、环境和负载，说明改动项与观测开销，重复运行并保留每次结果；条件不一致时不直接声称性能提升比例。

## 实施检查规则

P1a 起在实际 Module 中进行 gofmt、go vet、go test 和 API 构建；P1b 构建实际存在的 cmd/migrate，P4 Worker 存在后再增加该入口。并发变更运行相关 race 测试，数据链路变更运行对应故障和集成案例。前端运行实际定义的类型检查、构建和相关测试，Compose 文件存在后进行配置校验和运行验证。

P1a 阶段已按用户要求删除配置和 HTTP 测试文件，不迁移到其他目录或建立替代用例。由助手执行格式、静态检查、构建及 BASE-01/BASE-02 的真实进程检查；`go test` 的 `no test files` 记录为没有用例，不算行为测试通过。未复测的状态转换与并发行为在对应阶段报告中明确列出。

其余业务、前端、容器与性能案例在对应实现出现后再执行；不能使用“文档已写”代替“测试已通过”，也不能把删除基础测试解释为未来数据与并发功能无需验证。
