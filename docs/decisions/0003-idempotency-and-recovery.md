# 有界幂等与停写恢复决策

日期：2026 年 11 月 18 日。状态：纳入 V1.1 设计，P5 至 P6 完整实现。

## 背景

每次重试都生成随机 event_id 无法识别同一次操作；Redis 原子加一也不能覆盖标记过期、缓存丢失和任意日志重放。MySQL 故障与坏消息共用死信路径会丢失正常业务处理机会。

## 决策

使用带固定时间的 UUIDv7 request_id 和基于用户、房间、类型、请求的稳定 UUIDv5 event_id。Redis 记录请求指纹及冻结事件，重新发布窗口为 24 小时，记录保留到请求时间加 26 小时。UNKNOWN 允许原事件重试，不转成新的用户动作。

Redis 实时处理标记保留 9 天，Kafka 日志保留 7 天；保持固定分区和受控消费位置。MySQL consumer_inbox、业务数据和 worker_checkpoints 在同一事务提交，用于持久化去重与恢复依据。

Redis 数据不完整时暂停写入，固定 Kafka 屏障，等待 Worker 可靠持久化至屏障，重建新 epoch 的计数和近期幂等记录，再从屏障继续消费。业务完整性不能证明时保持不可写。

V1 以 MySQL failed_events 保存持久隔离记录。正常数据库故障暂停重试；格式与版本等异常可靠隔离后才允许推进检查点。

## 替代方式与取舍

同步 MySQL 请求账本或事务 Outbox 可以加强接收记录的持久性，但会让每条互动先承担数据库写入并增加一条发布流程。当前保留 Kafka 接受边界，采用有界 Redis 记录及停写恢复，代价是 Redis 异常时降低写可用性。

在线重建及跨快照并发追增量需要额外协调，第一版采用单 API 的维护窗口。窗口外不承诺无限期重试；任意回退实时位移必须经过重建，不在现有计数上重复累计。

9 天事件键可能占用大量内存，必须在 P4/P5 测量预算并施加准入上限。该取舍适用于本地学习系统，不代表可以以同一结构无成本扩展到大规模流量。
