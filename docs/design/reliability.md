# LiveStream 幂等与故障恢复设计

基线 V1.1。以下完整保证适用于 P6 完成后的 Kafka 模式，P3 至 P5 的阶段限制见 [开发计划](../development-plan.md)。本设计采用至少一次处理和业务去重，接受确认、实时展示与数据库持久化是三个不同结果。

## 请求身份与时间窗口

客户端为每次新的 DANMAKU 或 LIKE 动作生成 UUIDv7 request_id，重试保留原值。服务端规范化为小写后，从 UUID 的时间部分校验窗口：首次准入和重新发布时不得早于当前时间 24 小时，不得晚于当前时间 5 分钟。过旧返回 REQUEST_EXPIRED，未来偏差过大返回 CLOCK_SKEW。过期不代表原动作没有发生；已无记录可查时按 WebSocket 契约保留 unknown。

幂等范围是 user_id、room_id、客户端消息 type、request_id 四元组，用户与房间来自已认证连接。event_id 使用 UUIDv5，命名空间固定为 RFC URL namespace 6ba7b811-9dad-11d1-80b4-00c04fd430c8，UTF-8 name 固定为 livestream/v1/{user_id}/{room_id}/{type}/{request_id}。UUIDv7 时间字段与 UUIDv5 命名生成方式见 [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)。这里的事件标识不承担密码或签名用途。

请求指纹为 SHA-256：DANMAKU 输入为 type、换行、room_id、换行、原始合法 content；LIKE 输入为 type、换行、room_id、换行。分隔换行是单个 LF；字符串为 UTF-8，不包含额外末尾换行，LIKE 的内容部分为空。仅允许协议规定字段，因此不存在未计入指纹的业务参数。

同一范围相同指纹复用结果；不同指纹返回 REQUEST_CONFLICT。客户端修改内容或主动再次点赞属于新的动作，必须使用新的 request_id；网络重试不得自动换 ID。

采用时间自带的 UUIDv7，是为了拒绝将过期旧请求伪装成新的重试。业务结果只在明确窗口内可重新发布，不能通过延长 Redis TTL 获得无限期重新计数能力。

## 请求记录与准入顺序

Redis request 记录保存完整冻结事件、指纹、event_id、admitted_at、状态、accepted_at、发布租约及持有者。绝对过期时间为 request_id 内时间加 26 小时，重试不续期。已经 ACCEPTED 的记录在保留期内可返回结果；超过 24 小时的 UNKNOWN 不再重新发布。

准入顺序为：身份与输入校验 → 查询已有请求并比较指纹 → 对新请求检查房间开放状态和限流 → 在房间准入锁内原子登记请求 → 在锁外发布。已有接受结果可以在房间关闭后返回；在途请求是否可继续按 [领域规则](domain-model.md) 判断。

每条新请求最多一个发布者获得 10 秒租约，执行中每 3 秒续租；租约写入与状态修改使用持有者比较，不允许过期发布者覆盖新持有者状态。并发重复请求返回 REQUEST_IN_PROGRESS。发布者崩溃或超时后可以重新发布同一冻结事件，不能生成另一个 event_id。

| 状态 | 意义 | 后续行为 |
| --- | --- | --- |
| PUBLISHING | 已准入，正在发送 | 其他请求等待；失去租约视为待核实 |
| ACCEPTED | 已取得 Broker 成功确认，或从已持久化事件恢复 | 直接返回同一 event_id 的 ACK |
| UNKNOWN | 可能已写入，尚不能确认 | 在窗口内获取租约后用原事件重试 |

纯输入、权限、限流和发布前依赖检查失败不创建接受记录。请求一旦开始发送，不能因为超时改写成“确定未执行”。Producer 网络错误可能发生在日志提交之后，此边界依据 [Kafka 投递语义](https://kafka.apache.org/44/design/design/#message-delivery-semantics)。

## 接受确认及客户端结果

单次发布最长等待 5 秒，内部最多 3 次有界重试，退避包含在总时限内。Kafka 明确确认成功后记录 ACCEPTED 并返回 ACK；若 Broker 已成功而 Redis 状态更新失败，业务仍已被接受，可返回 ACK，但立即将写能力置为不可用，完成恢复前不接收新操作。

无法证明未发送的错误返回 RESULT_UNKNOWN。客户端以同一身份和请求重试；即使应用层重复发布，事件身份不变，实时与持久化消费者各自去重。Kafka Producer 幂等不代替这层业务幂等。

ACK 不保证广播或落库；广播不必等待 ACK 写入连接。客户端将同一事件的本地待确认项、ACK、实时广播和历史记录合并。离线必达不在 V1 范围。

## Redis 实时投影

实时消费者按分区顺序处理。一个短 Lua 操作完成事件标记检查、首次 LIKE 的计数和 revision 增加、必要的房间投影初始化检查，以及该分区 Redis next_offset 更新。禁止先 SET 去重标记、后单独 INCR。脚本原子执行能力见 [Redis Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

脚本先校验键类型、计数格式和溢出边界再执行写入。脚本报错或调用结果未知时不假定数据已全部回滚：暂停该投影并核对状态，无法证明完整时进入恢复，不对可能部分完成的操作盲目重试。

重复事件不增加计数或 revision，但允许推进该次日志记录的连续处理位置。首次弹幕只写事件处理标记和位移，然后尝试广播。投影更新成功且广播已尝试入队后才提交 Kafka 实时消费位移；无在线连接时广播也可完成处理。队列满关闭对应慢连接，不等待所有客户端确认。

业务广播失败不回滚已接受事件或计数。客户端通过状态快照校正计数、通过已落库历史补查弹幕。更新 Redis 后进程崩溃可能导致一次即时广播未送达，这符合在线尽力推送的边界。

点赞总数及房间投影元数据不设置 TTL。事件处理标记保留 9 天；Kafka 保留 7 天，合法重新发布窗口为 24 小时，剩余一天作为边界余量。此设计仅支持正常位移恢复和本节定义的全量重建；禁止在现有计数上任意回退消费者位移。

不将 Kafka 的保留配置当作每条记录严格的最大存活时间。实时消费者遇到准入 timestamp 距当前时间达到 8 天的积压记录时停止在线投影，转入全量恢复，避免标记已过期仍重复加数；Worker 仍按事件身份处理有效旧记录。消费组位移不存在但已有投影或数据库历史时视为进度丢失，不能按全新空系统从 earliest 直接累加。

Redis 使用 noeviction。写入内存不足时停止接收，不通过自动淘汰请求或处理标记维持表面可用性。容量预算见数据设计。TTL、Kafka 保留期和重试窗口必须一并修改及验证，不能单独缩短标记期限。

P6 起，最早未持久化事件的年龄达到 6 天或 Kafka 数据卷剩余空间低于 20% 时，停止新的业务准入并暴露积压告警；该阈值为恢复预留时间，不保证日志永不淘汰。停止生产不会停止保留期计时，数据库恢复或保留期调整必须在日志实际丢失之前完成。

## 运行前的一致性检查

Redis 保存 projection_epoch、各分区 next_offset 和投影 READY 标记。Kafka 集群及 topic 身份发生变化时停止运行，不能把同名新 Topic 当作旧日志。

启动及 Redis 断连重连后，比较 Redis 处理位置和 live-realtime 已提交位置：Redis 可以领先于提交位置，重读会通过标记去重；Redis 落后于已提交位置、epoch 缺失、应存在的房间计数缺失，或无法证明状态完整时，进入 RECOVERING。

已知新建房间在允许第一条事件之前原子建立零值投影。其他缺失计数一律不按零初始化。不能仅看到一个全局 READY 键就忽略房间数据完整性。

## Redis 丢失后的恢复步骤

V1 选择可解释的停写恢复，允许本地维护窗口。恢复负责人执行下列操作并记录每步结果；步骤失败时维持不可写，不切换半成品投影。

1. API 拒绝新业务写入、关闭旧 WebSocket 连接和票据签发，报告 RECOVERING；暂停 live-realtime，冻结并排空所有生产者。无法确认旧发布者已经停止时不继续。
2. 记录 live.events 每个分区当前日志末端的 next_offset，形成固定屏障 B。Worker 继续处理至 B，等待各分区数据库 checkpoint 达到 B，并停止在 B；屏障之后不得有新的生产。
3. 检查所需日志是否仍保留，且 B 之前的隔离记录均已完成业务修复，或有证据表明只是未代表合法业务的外来无效记录。若存在日志缺口、无法修复的合法事件或数据库不可用，保持恢复未完成，明确报告损失范围；不能只检查隔离行的状态标签。
4. 在一致数据库快照内按 interaction_events 的唯一事件计算每个房间的全部点赞数；创建新 epoch，写入新一代 Redis 键，各房间 revision 从 "0" 开始，不覆盖仍可诊断的旧代键。MySQL 事件在 V1 不自动清理。
5. 从 consumer_inbox 恢复最近 9 天事件的处理标记；按 request_id 的时间恢复仍在 26 小时记录保留期内的请求，状态设为 ACCEPTED，使用保存的完整事件和指纹，accepted_at 无法还原时为 null。没有进入日志的准入记录不算接受，重试仍受稳定 event_id 和时间窗口约束。
6. 将新投影各分区 next_offset 设置为 B，在 MySQL 记录恢复批次和屏障；确认房间数、总数与抽样结果一致，再切换 active epoch，并将 live-realtime 的消费位置设置为 B。
7. 恢复 Worker、实时消费者及票据签发，最后开放新业务写入。客户端重新建立连接取得新快照，不能沿用旧 epoch 的增量。恢复中断时从恢复批次记录核对并继续，不能同时启用两个 epoch。

屏障保证数据库汇总与后续增量不重复覆盖同一段事件。MySQL 异步持久化尚未完成时，不可直接 COUNT 后再从任意 Kafka 位移继续消费。

恢复要求已接受事件仍在 Kafka 保留范围内或已可靠落库。Kafka 单节点及 MySQL 同时丢失数据，或日志已过期而 Worker 未持久化时，不能宣称无损恢复。

## Worker 事务与失败分类

Worker 以 event_id 在 consumer_inbox 中去重，并在同一 MySQL 事务内写入业务表及该分区 next_offset 检查点。重复事件需比较指纹，匹配才跳过业务写入；冲突事件隔离。事务成功后才提交 Kafka 位移；Kafka 提交失败可重新消费，数据库去重保证业务不重复。

| 故障 | 处理及位移 |
| --- | --- |
| MySQL 不可用、连接断开、可重试死锁 | 回滚且不推进位移；每轮最多重试 5 次，之后暂停分区，每 30 秒探测恢复，不把正常事件送入死信 |
| 已验证永久不合法的格式、未知 schema_version、事件指纹冲突 | 在 failed_events 保存完整原始记录和原因，连同检查点在事务中提交，然后才推进 Kafka 位移 |
| 隔离记录保存失败 | 不提交、不跳过，按数据库故障处理 |
| Redis 实时处理失败 | 不推进实时位移；影响写能力时拒绝新准入，不自动切换直接广播 |
| 实时消费者遇到非法事件 | 暂停该分区及相关写能力，等待 Worker 隔离、修复和受控恢复，不静默跳过 |
| 消费者分区被撤销或进程退出 | 停止取新批次，已完成事务的连续位置可提交；未完成部分回滚后交接 |

V1 的“死信”落在 MySQL failed_events，不增加跨 Kafka Topic 的双写事务。隔离后的事件仍是未完成业务，不能将 checkpoint 前进解释为全部业务成功。修复后从隔离记录重新执行原事件的持久化事务，保留原 event_id；修改原业务内容或丢弃记录必须作为可追踪的人工决策，不能自动处理。

## 故障可见性

记录未知发布数、请求冲突数、处理重复数、隔离未解决数、暂停分区、数据库 checkpoint、Kafka 提交位移和日志保留起点。隔离记录未清零时，持久化完整性状态为 degraded；计数重建不得绕过该状态。

MySQL 临时不可用时，依赖数据库的登录、房间变更、新握手和历史查询返回依赖错误；已经认证、已缓存开放状态且身份未到期的现有连接，可以在 Redis、Kafka 正常且积压预算允许时继续接受事件。房间状态只能由本 API 修改，关闭事务失败不改变缓存。Worker 独立暂停，其恢复不要求 API 重建在线连接。

验收通过 [IDEM、KAFKA 和 REC 案例](../verification/plan.md) 建立。具体可执行脚本随实现提供，本设计不代表故障演练已经执行。
