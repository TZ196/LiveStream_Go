# LiveStream 幂等与故障恢复设计

基线 V1.1。点赞从 P4 首次交付即采用 Kafka；完整的历史和恢复保证适用于 P6 完成后，阶段限制见 [开发计划](../development-plan.md)。本设计采用至少一次处理和业务去重，接受确认、实时展示与数据库持久化是三个不同结果。

## 请求身份与时间窗口

客户端为每次新的 DANMAKU 或 LIKE 动作生成 UUIDv7 request_id，重试保留原值。服务端规范化为小写后，从 UUID 的时间部分校验窗口：首次准入和重新发布时不得早于当前时间 24 小时，不得晚于当前时间 5 分钟。过旧返回 REQUEST_EXPIRED，未来偏差过大返回 CLOCK_SKEW。过期不代表原动作没有发生；已无记录可查时在后台保留未确认结果，不向前端发送 Kafka 内部未知结果，也不伪称确定失败。

幂等范围是经认证的 `user_id` 与规范小写 `request_id` 的组合；同一用户不得用相同 ID 创建不同房间、场次、类型或内容的操作。服务端 event_id 使用 UUIDv5，命名空间固定为 RFC URL namespace `6ba7b811-9dad-11d1-80b4-00c04fd430c8`，UTF-8 name 为 `livestream/v2/{user_id}/{request_id}`。这是尚未实现的新契约，不能与原先的 v1 输入混用。UUIDv7 时间字段与 UUIDv5 规则见 [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)。

请求指纹为 SHA-256：UTF-8 内容为 `type`、LF、规范十进制 `room_id`、LF、规范十进制 `session_id`、LF、业务内容；DANMAKU 内容为原始合法 content，LIKE 内容为空，因此 LIKE 的编码最后一个字节是 LF。LIKE 固定 +1 且 data 必须为 `{}`；不接受 count 等额外字段。服务器使用认证身份及校验后的场次构造指纹，不信任客户端宣称的身份。

同一用户的相同 request_id 和业务内容代表同一次操作，重试保留原 event_id、场次、事件时间和内容，不合并后续点击。同一 ID 携带不同内容属于客户端协议错误；没有发布前登记时，服务端无法在发送前识别和拒绝此冲突，两个版本都可能进入 Kafka。消费者分别比较 event_id 的指纹，发现冲突时停止受影响分区并告警；P6 实现持久隔离后再按隔离规则处理。若冲突涉及不同房间，Key 可能进入不同分区，两个消费组可能先看到不同版本，不能承诺自动选择同一个版本，必须停止并人工核对。

## 准入与发送

点赞顺序：身份、输入、时间窗口及场次准入校验 → 构造确定性事件 → Kafka Producer。发布前不读写 Redis 请求指纹、不登记状态、不更新点赞数；Redis 在实时消费阶段原子去重和累加。重试原请求时可能再次向 Kafka 发布同一个 event_id，这是允许的；客户端必须保留原始请求。场次关闭后的旧请求无法凭不存在的登记证明其曾准入，如何安全重试和查询长期未确认结果必须在上线前解决，不能将它改绑新场或断言未发生。

Producer 启用幂等及 acks=all；获得 Broker 成功确认后才能返回接受 ACK。发送超时可能已经写入，不能伪报成功或确定未发生；应用层重试保持原事件。ACK 不代表 Redis 已更新、广播已送达或 MySQL 已落库。Kafka 单节点、保留期耗尽、存储损坏或客户端丢失原请求等情况都可能造成数据丢失或未决，不承诺任何故障下无损。

## Redis 实时投影

实时消费者按各分区顺序处理；同一房间的点赞可能由不同分区交错到达。一个短 Lua 操作完成事件标记检查、首次 LIKE 的计数和 revision 增加、必要的房间投影初始化检查，以及该分区 Redis next_offset 更新。同一 Redis standalone 实例对这些脚本串行执行，计数和 revision 的单调性以实际原子提交顺序为准，不依赖 Kafka 跨分区顺序。禁止先 SET 去重标记、后单独 INCR。脚本原子执行能力见 [Redis Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

脚本先校验键类型、计数格式和溢出边界再执行写入。脚本报错或调用结果未知时不假定数据已全部回滚：暂停该投影并核对状态，无法证明完整时进入恢复，不对可能部分完成的操作盲目重试。

重复事件不增加计数或 revision，但允许推进该次日志记录的连续处理位置。首次弹幕只写事件处理标记和位移，然后尝试广播。投影更新成功且广播已尝试入队后才提交 Kafka 实时消费位移；无在线连接时广播也可完成处理。队列满关闭对应慢连接，不等待所有客户端确认。

业务广播失败不回滚已接受事件或计数。客户端通过状态快照校正计数、通过已落库历史补查弹幕。更新 Redis 后进程崩溃可能导致一次即时广播未送达，这符合在线尽力推送的边界。

点赞总数及房间投影元数据不设置 TTL。事件处理标记保留 9 天；Kafka 保留 7 天，合法重新发布窗口为 24 小时，剩余一天作为边界余量。此设计仅支持正常位移恢复和本节定义的全量重建；禁止在现有计数上任意回退消费者位移。

不将 Kafka 的保留配置当作每条记录严格的最大存活时间。实时消费者遇到客户端请求时间 timestamp 距当前时间达到 8 天的积压记录时停止在线投影，转入全量恢复，避免标记已过期仍重复加数；Worker 仍按事件身份处理有效旧记录。消费组位移不存在但已有投影或数据库历史时视为进度丢失，不能按全新空系统从 earliest 直接累加。

Redis 使用 noeviction。写入内存不足时停止接收，不通过自动淘汰请求或处理标记维持表面可用性。容量预算见数据设计。TTL、Kafka 保留期和重试窗口必须一并修改及验证，不能单独缩短标记期限。

P4 Worker 交付后，最早未持久化事件的年龄达到 6 天或 Kafka 数据卷剩余空间低于 20% 时，停止新的业务准入并暴露积压告警；该阈值为恢复预留时间，不保证日志永不淘汰。停止生产不会停止保留期计时，数据库恢复或保留期调整必须在日志实际丢失之前完成。

## 运行前的一致性检查

Redis 保存 projection_epoch、各分区 next_offset 和投影 READY 标记。Kafka 集群及 topic 身份发生变化时停止运行，不能把同名新 Topic 当作旧日志。

启动及 Redis 断连重连后，比较 Redis 处理位置和 live-realtime 已提交位置：Redis 可以领先于提交位置，重读会通过标记去重；Redis 落后于已提交位置、epoch 缺失、应存在的房间计数缺失，或无法证明状态完整时，进入 RECOVERING。

已知新场次在允许第一条事件之前原子建立 session_id 对应的零值投影。其他缺失计数一律不按零初始化。不能仅看到一个全局 READY 键就忽略房间数据完整性。

## Redis 丢失后的恢复步骤

V1 选择可解释的停写恢复，允许本地维护窗口。恢复负责人执行下列操作并记录每步结果；步骤失败时维持不可写，不切换半成品投影。

1. API 拒绝新业务写入、关闭旧 WebSocket 连接和票据签发，报告 RECOVERING；暂停 live-realtime，冻结并排空所有生产者。无法确认旧发布者已经停止时不继续。
2. 记录 live.events 每个分区当前日志末端的 next_offset，形成固定屏障 B。Worker 继续处理至 B，等待各分区数据库 checkpoint 达到 B，并停止在 B；屏障之后不得有新的生产。
3. 检查所需日志是否仍保留，且 B 之前的隔离记录均已完成业务修复，或有证据表明只是未代表合法业务的外来无效记录。若存在日志缺口、无法修复的合法事件或数据库不可用，保持恢复未完成，明确报告损失范围；不能只检查隔离行的状态标签。
4. 在一致数据库快照内按 interaction_events 的唯一事件分别计算每个场次的点赞数；创建新 epoch，写入新一代 Redis 键，各场次 revision 从 "0" 开始，不覆盖仍可诊断的旧代键。MySQL 事件在 V1 不自动清理。
5. 从 consumer_inbox 恢复最近 9 天事件的处理标记及指纹。发布结果未知且未出现在日志或数据库中的请求不能简单认定为未接受；客户端需保留原请求，长期结果核对机制仍待设计。
6. 将新投影各分区 next_offset 设置为 B，在 MySQL 记录恢复批次和屏障；确认场次数、各场总数与抽样结果一致，再切换 active epoch，并将 live-realtime 的消费位置设置为 B。
7. 恢复 Worker、实时消费者及票据签发，最后开放新业务写入。客户端重新建立连接取得新快照，不能沿用旧 epoch 的增量。恢复中断时从恢复批次记录核对并继续，不能同时启用两个 epoch。

屏障保证数据库汇总与后续增量不重复覆盖同一段事件。MySQL 异步持久化尚未完成时，不可直接 COUNT 后再从任意 Kafka 位移继续消费。

恢复要求已接受事件仍在 Kafka 保留范围内或已可靠落库。Kafka 单节点及 MySQL 同时丢失数据，或日志已过期而 Worker 未持久化时，不能宣称无损恢复。

## Worker 事务与失败分类

Worker 以 event_id 在 consumer_inbox 中去重，点赞业务表必须有 event_id 唯一索引，并在同一 MySQL 事务内写入业务表及该分区 next_offset 检查点。重复事件需比较指纹，匹配才跳过业务写入；冲突事件隔离。事务成功后才提交 Kafka 位移；Kafka 提交失败可重新消费，数据库去重保证业务不重复。

| 故障 | 处理及位移 |
| --- | --- |
| MySQL 不可用、连接断开、可重试死锁 | 回滚且不推进位移；每轮最多重试 5 次，之后暂停分区，每 30 秒探测恢复，不把正常事件送入死信 |
| 已验证永久不合法的格式、未知 schema_version、事件指纹冲突 | 在 failed_events 保存完整原始记录和原因，连同检查点在事务中提交，然后才推进 Kafka 位移 |
| 隔离记录保存失败 | 不提交、不跳过，按数据库故障处理 |
| Redis 实时处理失败 | 不推进实时位移；影响写能力时拒绝新准入，不自动切换直接广播 |
| 实时消费者遇到非法事件 | 暂停该分区及相关写能力，等待 Worker 隔离、修复和受控恢复，不静默跳过 |
| 消费者分区被撤销或进程退出 | 停止取新批次，已完成事务的连续位置可提交；未完成部分回滚后交接 |

P4 的 failed_events 尚未交付，遇到非法或冲突事件应暂停分区、不推进位移并告警；下述持久隔离流程自 P6 交付后适用。V1 的“死信”落在 MySQL failed_events，不增加跨 Kafka Topic 的双写事务。隔离后的事件仍是未完成业务，不能将 checkpoint 前进解释为全部业务成功。修复后从隔离记录重新执行原事件的持久化事务，保留原 event_id；修改原业务内容或丢弃记录必须作为可追踪的人工决策，不能自动处理。

## 故障可见性

记录未知发布数、请求冲突数、处理重复数、隔离未解决数、暂停分区、数据库 checkpoint、Kafka 提交位移和日志保留起点。隔离记录未清零时，持久化完整性状态为 degraded；计数重建不得绕过该状态。

MySQL 临时不可用时，依赖数据库的登录、房间变更、新握手和历史查询返回依赖错误；已经认证、已缓存开放状态且身份未到期的现有连接，可以在 Redis、Kafka 正常且积压预算允许时继续接受事件。房间状态只能由本 API 修改，关闭事务失败不改变缓存。Worker 独立暂停，其恢复不要求 API 重建在线连接。

验收通过 [IDEM、KAFKA 和 REC 案例](../verification/plan.md) 建立。具体可执行脚本随实现提供，本设计不代表故障演练已经执行。
