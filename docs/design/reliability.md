# LiveStream 幂等与故障恢复设计

基线 V1.1。点赞从 P4 首次交付即采用 Kafka；点赞已具备正常重启核验与异常数据重建；弹幕历史及 V8 持久异常隔离已接入，点赞异常隔离仍待后续阶段，阶段限制见[开发计划](../development-plan.md)。本设计采用至少一次处理和业务去重，接受确认、实时展示与数据库持久化是三个不同结果。

先带着三个问题阅读：客户端重试怎样识别原操作；Kafka 重放怎样避免重复业务效果；存储丢失后如何证明可以恢复。请求登记可从 [弹幕 Service](../../backend/internal/danmaku/service.go) 和 [Redis 请求状态](../../backend/internal/danmaku/requests.go)追踪；持久化分别看[点赞事务](../../backend/internal/likes/persistence.go)和[弹幕事务](../../backend/internal/danmaku/persistence.go)；两类缓存恢复入口是 [点赞 recovery](../../backend/internal/likes/recovery.go) 与 [最近弹幕 recovery](../../backend/internal/danmaku/recent_recovery.go)。

## 请求身份与时间窗口

代码入口：[弹幕事件构造](../../backend/internal/danmaku/event.go)的 `NewRequest`、[点赞事件构造](../../backend/internal/likes/event.go)的 `NewLikeBatch`。先区分客户端的 `request_id` 与服务端稳定推导的 `event_id`，再看各自的重试规则。

客户端为每条弹幕和每个 500 毫秒点赞批次生成 UUIDv7 request_id。首发时冻结批次，重试保留原值与点击数。服务端要求规范小写 UUIDv7，从 UUID 的时间部分校验窗口：首次准入和重新发布时不得早于当前时间 24 小时，不得晚于当前时间 5 分钟。过旧返回 REQUEST_EXPIRED，未来偏差过大返回 CLOCK_SKEW。过期不代表原动作没有发生；已无记录可查时在后台保留未确认结果，不向前端发送 Kafka 内部未知结果，也不伪称确定失败。

幂等范围是经认证的 `user_id` 与规范小写 `request_id` 的组合；同一用户不得用相同 ID 创建不同房间、场次、类型或内容的操作。服务端 event_id 使用 UUIDv5，命名空间固定为 RFC URL namespace `6ba7b811-9dad-11d1-80b4-00c04fd430c8`，UTF-8 name 为 `livestream/v2/{user_id}/{request_id}`。点赞版本 1 和 2 共用这一事件身份。UUIDv7 时间字段与 UUIDv5 规则见 [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)。

请求指纹对 UTF-8 字节计算 SHA-256。点赞前缀依次为 `LIKE_CLICKED`、LF、规范十进制 room_id、LF、规范十进制 session_id、LF。数量为 1 时直接对此前缀散列，兼容旧单击。数量大于 1 时在前缀后追加十进制 count 和一个 LF。弹幕指纹为 SHA-256("DANMAKU_SENT\n" + room_id + "\n" + session_id + "\n" + 原始合法 content)，末尾不补 LF。服务端用认证身份及校验后的场次构造事件。

同一用户的相同 request_id 和业务内容代表同一次操作，重试保留原 event_id、场次、事件时间和内容，不合并后续点击。客户端不得跨业务复用 ID；各业务分别维护登记及持久化去重，未建立跨业务请求账本。点赞同一 ID 携带不同数量或其他不同内容属于客户端协议错误；点赞没有发布前登记时，服务端无法在发送前识别和拒绝此冲突，两个版本都可能进入 Kafka。消费者分别比较 event_id 的指纹，发现冲突时停止受影响分区并告警；P6 实现持久隔离后再按隔离规则处理。若冲突涉及不同房间，Key 可能进入不同分区，两个消费组可能先看到不同版本，不能承诺自动选择同一个版本，必须停止并人工核对。

## 准入与发送

点赞顺序：身份、输入、时间窗口及场次准入校验 → 构造确定性事件 → Kafka Producer。发布前不读写 Redis 请求指纹、不登记状态、不更新点赞数；Redis 在实时消费阶段原子去重和累加。重试原请求时可能再次向 Kafka 发布同一个 event_id，这是允许的；客户端必须保留原始请求。场次关闭后的旧请求无法凭不存在的登记证明其曾准入，如何安全重试和查询长期未确认结果必须在上线前解决，不能将它改绑新场或断言未发生。

Producer 启用幂等及 acks=all；获得 Broker 成功确认后才能返回接受 ACK。发送超时可能已经写入，不能伪报成功或确定未发生；应用层重试保持原事件。ACK 不代表 Redis 已更新、广播已送达或 MySQL 已落库。Kafka 单节点、保留期耗尽、存储损坏或客户端丢失原请求等情况都可能造成数据丢失或未决，不承诺任何故障下无损。

## 弹幕登记、审核与结果核对

沿 [Submit](../../backend/internal/danmaku/service.go) 从上到下阅读；原子登记和限流由 [begin_request.lua](../../backend/internal/danmaku/lua/begin_request.lua) 完成，审核实现在 [moderation.go](../../backend/internal/danmaku/moderation.go)。

弹幕 Service 顺序为：构造并校验身份/指纹 → Redis 查原状态，缺失时查询 MySQL 最终结果 → 新请求原子限流和登记 → AC 审核 → 用户名快照及完整事件冻结 → Kafka 发布 → 接受确认。只有 Broker 确认成功或完整 SQL 明细证明原事件存在时返回 ACK。PROCESSING 不是接受证明。

Redis Lua 将请求指纹、状态检查与每用户每房间 10 秒/10 条滑动窗口放在一次原子操作中。同房间多个页面共享额度，不同房间独立；窗口不按开播场次重置。首次审核拒绝也计一次；同请求重试不再次占额度。PROCESSING 有 15 秒执行权与随机 owner，避免并发重试同时重造事件。REJECTED 返回原类别，ACCEPTED 返回原 event_id；请求身份仍按用户和 request_id 唯一，相同 ID 改变内容、房间或场次返回 REQUEST_CONFLICT。通过审核后冻结原文、用户名、事件时间和词库版本，发布错误时保留完整冻结事件。词库修改重启后，重试不重新审核已冻结或已接受事件。脚本位于 internal/danmaku/lua 并嵌入程序，Go 不再内联 Lua 源码。

请求记录保留至 UUIDv7 时间 + 25 小时；重新发布只允许 24 小时内。缓存损坏、原记录丢失且无法证明结果时返回 REQUEST_IN_PROGRESS/outcome=pending；前端保留原请求，有限重试，不能自动改 ID 或放行后续排队弹幕。已关闭场次的冻结但未确认请求保持未确认，可查询历史；不会转发到新场次。

Redis 实例 run_id 变化、请求身份键丢失或回退时，无法单靠 MySQL 判断尚未落库的 Kafka 发布。当前选择保守保护：登记截止时间为 Redis 当前时间 + 5 分钟，覆盖允许的客户端未来时钟偏差。截止时间之前的缺失请求不重造事件；保留下来的完整冻结事件或 SQL 接受证据仍可核对。保护期间普通新弹幕暂停发送，草稿保留；之后新生成请求恢复准入。API 普通重启沿用同一 Redis 身份，无此等待。**因此，即使 AOF 数据完整，Redis 进程重启也可能触发弹幕五分钟保护；点赞仍使用原投影完整性检查，可以单独恢复。** 不以牺牲冻结审核版本换取立即放行。

这不是 MySQL 请求账本或 Outbox，不保证任意部分键损坏下还原全部请求。无原冻结事件、无 SQL 结果且 Kafka 尚未持久化的旧请求可能长期未确认；不能用当前词库伪造旧事件，不能宣称端到端恰好一次。需要更强保证时另行设计耐久请求账本，本轮不建设恢复任务管理平台。

AC 使用 rune Trie、Failure Link 和输出传播，启动后只读并发扫描。词库与输入均执行 NFKC、小写及移除 U+200B/U+FEFF；保留普通空格、标点及 ZWJ。只在审核副本匹配，原文不改变。内部命中位置是审核副本的码点 [start,end)，不映射原文；对外只给拒绝类别。80 条人工种子词及整理依据见 configs/moderation_words.tsv；不能识别所有谐音、语境、拼音或隐晦表达。词库修改重启生效，格式错误只禁止新弹幕，不回溯审核 Kafka 记录。

### 弹幕广播与持久化

同用户同房间进入固定分区并串行消费；第一版由单 API 承载房间。不同分区通过每活跃场次容量 128 的队列串行分发，按统一次序复制收件人并在锁外向连接非阻塞入队。每连接唯一写循环、容量 128；满队列仅关闭该慢连接。场次缓存最多 5000 个完整事件去重，回收场次后缓存释放，因此重放仍可能重复广播，前端必须去重。

实时组分发后推进独立 Redis next_offset，再提交本组 Kafka 位移。该进度用于 Topic 身份和重放检查，不是数值投影。Kafka 已提交而本地进度丢失时允许沿已提交位置继续尽力推送，通过 SQL 历史补查；禁止将这一规则套用于点赞计数。旧场次迟到事件仍落库，不能进入新场次连接。

Worker 直接用 danmaku_messages 的两个唯一约束去重，核对完整冻结事件，明细与本组 checkpoint 在同一事务成功后才提交 Kafka。若 offset=100 处理完成，保存 next_offset=101。SQL 领先 Kafka 的正常重复窗口可安全重放；Kafka 超过 SQL 检查点、Topic 身份改变或所需日志过期时阻止消费，不自动跳到 latest。弹幕每条记录最多三次尝试，共用十秒期限，失败间等待 200、400 毫秒；永久格式错误、事件冲突及明确数据约束错误写入 failed_events 后继续处理下一条。依赖故障仍停止本组并退避重开。无新增审核组、死信 Topic 或自动修复服务。

弹幕两个组分别以 (consumer_group,topic_id,partition_id,record_offset) 唯一登记原始记录、完整哈希、尝试次数和错误摘要。Worker 隔离记录与自己的 next_offset 共用 MySQL 事务；实时组独立保存隔离记录、推进 Redis 分发位置，再提交本组 Kafka 位移，不写 Worker 检查点。任一步失败保留 Kafka 位移；重放核对原始内容，不重复新增或覆盖人工处置状态。正常大小消息保留完整原文，超长非法值的截断边界见[数据设计](database.md#消费与恢复表)。隔离只处理已明确定位的单条永久错误，不能用来解除 Topic 身份、日志缺口和恢复依据不足的保护。

共享 Manager 归 API 生命周期所有；点赞 CHECKING/RECOVERING/BLOCKED 不关闭共享连接、票据或弹幕。弹幕实时组异常不取消点赞循环；Worker 两条持久化循环互不取消。底层 Redis、Kafka、MySQL 和进程资源仍共享，整体依赖故障可能同时影响两项业务。

## Redis 实时投影

实时消费者按各分区顺序处理；同一房间的点赞可能由不同分区交错到达。一个短 Lua 操作完成事件标记检查、首次 LIKE 的计数和 revision 同时增加 count、必要的房间投影初始化检查，以及该分区 Redis next_offset 更新。同一 Redis standalone 实例对这些脚本串行执行，计数和 revision 的单调性以实际原子提交顺序为准，不依赖 Kafka 跨分区顺序。禁止先 SET 去重标记、后单独 INCR。脚本原子执行能力见 [Redis Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

脚本先验证投影元数据、Hash/ZSET 条数、指纹和分区进度，再对场次总数、revision、个人数逐位进行十进制整数加法。三个结果均在有符号 64 位范围内才写入。一次脚本提交个人数、前 100 名、场次计数、事件标记与检查点，重放原批次只允许推进连续位移。Redis 脚本错误不会自动回滚，出现未知结果或投影完整性错误时暂停并核对。

重复事件不增加计数或 revision，但允许推进该次日志记录的连续处理位置。弹幕使用独立 Topic 和分发进度，见下节，不进入点赞投影脚本。点赞在投影更新成功并为当前有观众的场次保留最新快照后，即可提交本组位移。每条 Kafka 消息的 10 秒业务期限涵盖投影写入、等待场次锁和位移提交。Redis 成功后若等锁超时，处理函数返回错误，保留未提交位移。重放时使用同一 Lua 返回的当前总数、个人数和榜单版本重新同步，各自比较版本。已同步的计数无需再次推送。恢复或重新连接时读取 Redis 首屏和榜单，即使没有下一条点赞也能校正页面。200 毫秒定时器独立推送快照，房间无人时仍完成计数。队列满关闭对应慢连接，不等待所有客户端确认。

业务广播失败不回滚已接受事件或计数。客户端通过状态快照校正计数、通过已落库历史补查弹幕。更新 Redis 后进程崩溃可能导致一次即时广播未送达，这符合在线尽力推送的边界。

点赞总数及房间投影元数据不设置 TTL。事件处理标记保留 9 天；Kafka 保留 7 天，合法重新发布窗口为 24 小时，剩余一天作为边界余量。此设计仅支持正常位移恢复和本节定义的全量重建；禁止在现有计数上任意回退消费者位移。

不将 Kafka 的保留配置当作每条记录严格的最大存活时间。实时消费者遇到客户端请求时间 timestamp 距当前时间达到 8 天的积压记录时停止在线投影，转入全量恢复，避免标记已过期仍重复加数；Worker 仍按事件身份处理有效旧记录。消费组位移不存在但已有投影或数据库历史时视为进度丢失，不能按全新空系统从 earliest 直接累加。

Redis 使用 noeviction。写入内存不足时停止接收，不通过自动淘汰请求或处理标记维持表面可用性。容量预算见数据设计。TTL、Kafka 保留期和重试窗口必须一并修改及验证，不能单独缩短标记期限。

后续告警目标（本轮尚未实现自动停写）：最早未持久化事件的年龄达到 6 天或 Kafka 数据卷剩余空间低于 20% 时，停止新的业务准入并暴露积压告警；该阈值为恢复预留时间，不保证日志永不淘汰。停止生产不会停止保留期计时，数据库恢复或保留期调整必须在日志实际丢失之前完成。

## 运行前的一致性检查

MySQL 的 projection_state 保存唯一有效 epoch 和 Topic UUID。配置中的 LIVESTREAM_PROJECTION_EPOCH 只用于首次兼容接入，普通重启继续使用数据库有效代次。Redis 每次启动改变 run_id，因此编号变化触发核验，不直接判定数据丢失。计数和读榜 Lua 在执行时检查已核验的 run_id，在线重启后不能未经检查继续计数或提交位移。

API 启动及 Redis 重连后，逐分区核对实时组提交位置与 Redis next_offset：一致时继续；Redis 领先时，核对领先区间的指纹后允许幂等重放；Redis 落后、身份缺失或场次数据不完整时进入重建。检查还按页核对所有个人数之和、前 100 名及保留日志内仍受保护的已处理事件标记。正常运行不要求两个消费组位移相等，正常重启不重置位移，也不建立异常恢复屏障 B。

CHECKING、READY、RECOVERING、BLOCKED 是点赞的内存状态。普通 API 的 /readyz 根据 HTTP 生命周期及 MySQL 判定；点赞单独通过房间 likes-state 接口报告，Worker 通过自身消费状态、错误和数据库检查点独立观察。恢复期间登录、注册和房间查询继续，改变场次的操作暂时拒绝。

已知新场次在允许第一条事件之前原子建立零值投影；历史缺失不能直接按零初始化。

### 为已有场次补建点赞榜

保留原投影代次和事件标记，在停写窗口从 MySQL 的唯一事件按场次、用户求 SUM(click_count)。专用命令先确认两个 Kafka 组无活跃成员，全部分区的组位移、日志末端及对应 Redis/MySQL 检查点一致。每场先写有一小时有效期的临时 Hash 和前 100 名，再核对汇总与现有总数、原投影版本及条目数，最后在一个 Redis 脚本中切换该场的键。结束时复核同一组位移屏障。失败时保持停写，排除原因后可以重复执行；使用正常读写前重新核对所有场次。操作步骤见[本地升级说明](../deployment.md#已有点赞数据升级到本场榜单)。

## Redis 丢失后的恢复步骤

当前采用单 API 与独立 Worker 的一次性恢复流程，不建设恢复任务表、接管或断点续建；恢复中再次掉电不在本轮交付范围。前端继续收集点击并按场次暂存，后端恢复窗口内暂停接收。

1. API 标记 RECOVERING，只停止点赞准入，保留共享票据、握手和连接。点赞准入锁等待本业务旧发送返回，随后排空 Producer，包括结果尚未确认的发送；实时消费组全部退出。
2. 读取 live.events 每个分区日志末端 next_offset，形成仅用于本次异常重建的内存屏障 B。Worker 继续持久化，等待每个分区的数据库检查点与持久化组提交位置达到 B；期间复核末端不变。后台没有新消息后 Worker 自然待机。
3. 检查尚未落库范围没有日志缺口，数据库检查点身份正确，点赞明细与 inbox 双向对应。在一致数据库快照内逐页重新验证冻结 JSON 的身份、指纹和 click_count；格式、冲突或必要日志缺失阻止恢复。Worker 未启动或暂时故障时等待，单轮恢复预算 2 分钟，超时保留不可用并退避重试。
4. 从 live_sessions 枚举所有场次，包括零赞和已结束场次；按 session_id、user_id 求 SUM(click_count)，在随机新 epoch 下构建总数、个人数和前 100 名。新代次 revision 从 "0" 开始。分页处理，保留旧代键供核对。
5. 从已验证的 inbox 恢复必要事件标记及 user_id:request_hash。以事件时间保留剩余 9 天保护窗口，超过窗口的已提交历史不补标记；合法重新发布仍限原请求 24 小时。新投影各分区 next_offset 设置为 B。
6. 核验新投影、Redis 运行编号及日志末端，确认实时组没有活跃成员，将其提交位置设置为 B 并读回。成功后更新 projection_state 的有效 epoch，重新组装实时依赖并开放点赞；共享连接接收新的能力与投影快照。
7. 客户端取得同场次的新 ROOM_STATE 后补发原待确认请求和新暂存点击。投影 epoch 可变化，原 request_id、场次和数量保持不变；关闭或切换场次时不挪用旧请求。

恢复条件不足时报告 BLOCKED 并记录内部原因，修复后重启 API 重新检查。正常网络故障和 Worker 等待不伪装为数据丢失。Kafka、Redis、MySQL 不存在跨系统原子切换，本轮不保证恢复切换中断后的自动续建。

屏障保证数据库汇总与后续增量不重复覆盖同一段事件。MySQL 异步持久化尚未完成时，必须先将检查点与屏障对齐，才能从该屏障继续消费。

恢复要求已接受事件仍在 Kafka 保留范围内或已可靠落库。Kafka 单节点及 MySQL 同时丢失数据，或日志已过期而 Worker 未持久化时，不能宣称无损恢复。

## Worker 事务与失败分类

先看 [点赞 `PersistLike`](../../backend/internal/likes/persistence.go) 和[弹幕 `Persist`](../../backend/internal/danmaku/persistence.go)怎样在同一事务内写业务和检查点，再看 [Worker 回调](../../backend/cmd/worker/main.go)及消费者何时提交 Kafka 位移。两种业务的去重表不同，不能只看函数名就假设相同实现。

Worker 以 event_id 在 consumer_inbox 中去重，点赞业务表必须有 event_id 唯一索引，并在同一 MySQL 事务内写入该批次的 click_count 及该分区 next_offset 检查点。重复事件需比较指纹，匹配才跳过业务写入；冲突事件隔离。事务成功后才提交 Kafka 位移；Kafka 提交失败可重新消费，数据库去重保证业务不重复。

| 故障 | 处理及位移 |
| --- | --- |
| MySQL 不可用、连接断开、可重试死锁 | 回滚且不推进位移；弹幕先在单条十秒预算内最多尝试三次，随后本组停止并退避三秒重开；点赞沿用原实现，不把正常事件送入死信 |
| 已验证永久不合法的格式、未知 schema_version、事件指纹冲突 | 弹幕有限重试后可靠隔离，再提交本组位置；点赞仍停止本业务组并告警，不推进未处理位移 |
| 隔离记录保存失败 | 不提交、不跳过，按数据库故障处理 |
| Redis 实时处理失败 | 不推进实时位移；影响写能力时拒绝新准入，不自动切换直接广播 |
| 实时消费者遇到非法事件 | 弹幕实时组独立隔离，不等待 Worker；隔离存储失败时保留位移并退避，相关弹幕能力暂时关闭；点赞沿用原恢复保护 |
| 消费者分区被撤销或进程退出 | 停止取新批次，已完成事务的连续位置可提交；未完成部分回滚后交接 |

V8 的“死信”落在 MySQL failed_events，当前只有弹幕接入，不增加跨 Kafka Topic 的双写事务。仓储先验证事件时间在 MySQL DATETIME 的 1000–9999 年范围内，避免驱动本地拒绝被误当成断连。明确持久化约束错误为 MySQL 1264、1292、1366、1406、1452、3819，分别涉及数值越界、非法日期/转换、非法值、超长值、外键及 CHECK；连接失败、死锁、缺表和未知 SQL 错误仍按依赖故障保留记录。隔离后的事件仍是未完成业务，不能将 checkpoint 前进解释为全部业务成功，也不广播被实时组判定为坏消息的记录。

隔离表默认 OPEN，当前不提供自动重放或管理界面。后续修复必须保留原 event_id；修改原业务内容或决定丢弃需记录依据和业务影响。原文已截断时不能声称可以完整重放。两个组独立处理，实时显示不以 SQL 落库为前置；若记录通过形状校验、但后来违反数据库约束，实时组可能已经展示，不能把 Worker 隔离解释为撤回广播。点赞隔离及其与恢复审计的衔接仍待另行实现。

## 故障可见性

记录未知发布数、请求冲突数、处理重复数、暂停组、数据库 checkpoint、Kafka 提交位移和日志保留起点。弹幕指标新增 consumer_failures_total，按组记录 retry、quarantined、quarantine_failed、dependency_failed；日志给出隔离来源位置和错误类别，未解决记录从 failed_events 的 OPEN 行查询。弹幕有未解决隔离记录时不能以 lag=0 声称历史完整；这些记录不属于点赞恢复依据，不阻断原点赞重建。将来接入点赞隔离时，必须同时扩展其完整性审计，不能只推进检查点。

MySQL 临时不可用时，依赖数据库的登录、房间变更、新握手和 MySQL 历史查询会受影响；当前每次新发布仍查询 MySQL 场次。已就绪的 Redis 最近弹幕查询本身不访问 MySQL；若缓存缺失，后台重建依赖 MySQL，因此不能保证恢复成功。现有连接可保留，但不能承诺数据库整体不可用时继续接受新事件。单个 Worker 事务故障与数据库整体停机应分开验证。房间状态由本 API 修改，关闭事务失败不改变已有状态。Worker 独立暂停，其恢复不要求 API 重建在线连接。

验收通过 [IDEM、KAFKA 和 REC 案例](../verification/plan.md) 建立。具体可执行脚本随实现提供，本设计不代表故障演练已经执行。

## 最近弹幕旁路缓存

先看 [recent.go](../../backend/internal/danmaku/recent.go) 怎样写入和分页，再看 [recent_recovery.go](../../backend/internal/danmaku/recent_recovery.go) 怎样取得锁、等待持久化检查点及替换缓存；HTTP 入口在 [danmaku.go](../../backend/internal/httpserver/danmaku.go)。

独立 `danmaku-recent-cache` 组消费 `live.danmaku`，以场次为单位写入 Redis ZSET，分数使用冻结的服务端接收时间；原子清理五分钟前的记录，每场最多保留最近 300 条。新增成员和恢复完成时，ZSET 与 READY 的过期时间均设为五分钟加 0–60 秒随机值，分散不同场次的过期时间；数据展示窗口仍严格为五分钟。相同成员的重复投递不刷新 TTL。若当前缓存中已有相同 `event_id` 的不同事件内容，保留先到版本、跳过冲突版本并记录告警。读取以成员排名分页，每次最多读取和返回 20 条。缓存只供最近展示，不是持久化证明；新消费组从最近五分钟开始，缓存消费者失败不阻断实时或持久化组。

为什么不让实时广播顺手等待缓存写入：独立组有自己的消费位置，缓存写入或重试不会成为实时组的同步前置。为什么使用成员作游标：分页脚本先清理过期项，再用 `ZREVRANK` 定位上一页最旧的完整成员，并在同一个 Lua 调用中读取后续成员；新弹幕插入不会让一个固定页号发生偏移，相同毫秒的成员也有各自位置。游标成员已过期时当前实现结束分页；满 20 条时可能给出游标，下一页仍可能为空。实现见 [recent_page.lua](../../backend/internal/danmaku/lua/recent_page.lua) 和 [recent.go](../../backend/internal/danmaku/recent.go)。

场次 READY 标志区分已初始化的空缓存和需要重建的缓存。缓存缺失时返回 `CACHE_WARMING`，最多四个后台任务跨场次运行；同场次用带期限的 Redis 锁合并重建请求。持锁期间缓存消费组暂停该场次写入，但不暂停广播。重建先记录 Topic UUID 与各分区末端，等待 MySQL 的弹幕持久化检查点追平；未解决的持久化隔离记录仅阻塞能够从原始消息中识别出所属房间的对应房间恢复。无法识别房间的隔离记录不阻塞恢复，优先其他房间可用，但可能使缓存遗漏无法归属的事件。随后分页读取已有弹幕表写入临时 ZSET，并在重建过程中应用同一条数上限。只有锁仍有效才原子替换并设 READY；锁过期的任务不可提交。屏障之后的事件由缓存消费组重试补入，因此恢复刚完成时仍可能存在短暂消费延迟。基本屏障和重建已在隔离环境验证，其他故障覆盖见[验证报告](../verification/reports/recent-danmaku.md)。单场最多 300 条不等于 Redis 实例内存已封顶；整体容量仍取决于五分钟内活跃场次数和负载，尚未测量。

前端收到 `CACHE_WARMING` 后最多自动重试 50 次：基准等待时间从 1 秒指数增长，最高 10 秒，每次乘以 0.8–1.2 随机系数且实际等待不超过 10 秒；等待期间其他加载入口不会绕过退避。成功后重置次数，切换场次或离开页面时取消定时器。退避只分散预热期间的重复请求，不能减少首次请求或证明热 Key 容量；实现见 [danmaku.ts](../../frontend/src/danmaku.ts)。

防穿透：数据库明确确认房间与场次不匹配时，持有恢复锁的任务在 READY 键写入 10 秒 `missing`；首次请求可能先收到预热，后续命中返回 404。数据库错误不会写入否定结果，锁过期的旧任务不能标记。有效空场次仍返回空列表。若被猜中的场次在这 10 秒内刚创建，否定标记可能短暂返回 404；有新弹幕写入会覆盖标记，最迟到期后重新校验。最近查询在单 API 内按认证用户每整分钟最多 120 次，最多记录 10000 个用户，超限返回 429 与 Retry-After；它是保护阈值，不是实测容量或多实例全局限流。随机 ID 仍可能在 TTL 内产生多个否定键，限流和恢复并发限制不能消除分布式滥用。Redis 故障不回源普通请求，查询降级为 503。

等待屏障是因为 Kafka 接受后 Worker 仍可能积压；若直接查 MySQL，会遗漏尚未持久化的事件。重建期间禁止该场次的缓存写入，是为了避免临时 ZSET 替换正式键时覆盖新消息；[recent_add.lua](../../backend/internal/danmaku/lua/recent_add.lua) 检查锁，[recent_finish.lua](../../backend/internal/danmaku/lua/recent_finish.lua) 核对锁持有者后才切换。锁到期不会让旧任务有权覆盖新结果，但缓存组需之后重新消费被阻塞的记录。

客户端 UUIDv7 时间仍用于请求身份和窗口校验，不作为最近缓存的时间。V2 在首次成功冻结事件时保存该次请求的服务端接收时间，重试沿用原值；MySQL 同样保存该值供重建，V1 由于缺少可信时间不进入最近缓存。API 主机与 Redis 的系统时间需要同步；服务器时钟发生跳变或两者存在偏差时，窗口仍会受时钟影响。该时间是请求接收时间，不是 Kafka Broker 的确认时间。
