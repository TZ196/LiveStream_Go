# LiveStream 领域模型与业务规则

基线 V1.1。负责业务口径与状态转换。接口字段由 [HTTP](api-spec.md) 和 [WebSocket](websocket-protocol.md) 定义，物理存储由 [数据设计](database.md) 定义。

## 对象及关系

User 表示注册账号；Room 表示由一个用户创建的长期互动房间；LiveSession 表示该房间一次独立开播场次；Connection 表示一次已认证且已注册到某一场次的连接；Danmaku 表示一次文本发送事件；LikeClick 表示一次点赞操作。场次模型为待实现设计，当前 P2 尚无场次表。

一个用户可以拥有多个房间，并在连接上限内同时打开多个页面。一条连接只属于一个房间、一个场次和一个用户；场次在握手或准入时绑定，不能因房间重开自动切换。关闭浏览器页面仅结束该连接，不关闭房间。

## 权限

| 行为 | 访客 | 已登录用户 | 当前房主 |
| --- | --- | --- | --- |
| 注册、登录 | 允许 | 允许 | 允许 |
| 查看房间及历史 | 拒绝 | 允许 | 允许 |
| 创建房间 | 拒绝 | 允许 | 允许 |
| 进入开放房间、弹幕、点赞 | 拒绝 | 允许 | 允许 |
| 结束直播、重新开播该房间 | 拒绝 | 拒绝 | 允许 |

客户端不得指定业务 user_id 或 owner_id。服务端从认证上下文确定操作者。V1 不提供用户改名、账号删除和房间删除接口。

## 用户及输入口径

- 用户名去除首尾 ASCII 空格后转为小写，使用 3 至 32 位 ASCII 字母、数字或下划线，首位为字母；规范化值唯一。
- 密码为 12 至 128 个 Unicode 字符、最多 512 个 UTF-8 字节，不自动去空格或截断。
- 房间标题去除首尾空白后为 1 至 80 个 Unicode 字符。
- 弹幕为 1 至 200 个 Unicode 字符，不能全部为空白；保留合法文本原样，不执行 HTML。大小限制和合法控制字符见 WebSocket 协议。
- 点赞为连续点击计数，同一用户可以多次点赞。它不表示“一人一票”，V1 不提供取消点赞。

## 房间状态

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| 不存在 | 合法用户创建 | OPEN，设置 owner_id 和 created_at，并创建首个独立场次 |
| OPEN | 房主结束直播 | CLOSED，设置本轮 closed_at，并结束当前场次 |
| CLOSED | 房主再次关闭 | 返回当前 CLOSED，不改写 closed_at |
| CLOSED | 房主重新开播 | OPEN，closed_at 清空，沿用原房间编号、所有者、标题和创建时间，并创建新的 session_id |
| OPEN | 房主再次开播 | 返回当前 OPEN，不重复创建房间 |
| CLOSED | 申请加入或新的弹幕、点赞 | 拒绝 ROOM_CLOSED |
| 任意已存在状态 | 非房主关闭或重新开播 | 拒绝 FORBIDDEN，不修改状态 |

OPEN 在页面显示为“直播中”，CLOSED 显示为“已结束”。结束的是本轮直播，房间本身长期保留；房主下次使用原房间重新开播，无需再创建。当前开播仅改变互动房间状态，不包含音视频推流。

关闭或重开不删除已接受事件及历史数据。每次从 CLOSED 转为 OPEN 都创建独立 session_id；点赞按 session_id 分别计数和持久化，重新开播不混入上一场。房间累计数若有需求可另行明确，不代替单场统计。房间状态来自 MySQL，RoomHub 中的状态只用于当前进程快速准入和连接管理。P3 目标实现应在同一事务中先锁定房间行，再同时更新房间和场次；同方向重试不能创建重复场次，交错反向操作按锁内执行顺序改变状态。当前 P2 仅有房间状态行锁，场次事务和每场计数尚未实现。

## 关闭与在途请求

Room Service 与消息准入共用进程内的房间准入锁。关闭请求在锁内完成权限检查和数据库状态更新，再将本地房间标为关闭；数据库更新失败时保留原开放状态。Kafka 发布及 WebSocket 网络写入不在房间锁中等待。

通过准入检查并登记到请求记录的操作属于在途操作。即使其 Kafka 确认晚于关闭，仍可返回原结果并持久化。关闭后首次出现的请求不允许准入。重试已有请求先查询记录：返回已有接受结果，或继续原在途操作，不作为新的点赞或弹幕。

RoomHub 在关闭后拒绝新注册，向已有连接发送 ROOM_CLOSED 并关闭。实时消费者对关闭场次的迟到事件仍更新该原场次的幂等记录和统计，但不再发送至已结束场次或后续场次的业务广播。点赞可能分布于多个分区：关闭本身只阻止新准入，不表示已准入点赞已全部持久化。若未来要求最终完成确认，不能只在一个分区写结束标记；必须先停止新准入，处理所有已准入发布者及结果未知的请求，再建立并核对覆盖所有相关分区的持久化屏障。无法确认旧发布者停止或在途结果时保持未完成；该屏障尚待单独设计和实现。

以上 RoomHub 和在途规则仍待 P3/P4/P5 实现。引入重开后还须隔离旧连接清理与新连接注册，用事件携带的 session_id 隔离上一轮迟到事件，避免其混入重新开播后的计数和即时消息；随 TODO-01/02 验收，P2 的数据库行锁不代表实时并发边界已完成。

## 在线连接及成员记录

online_count 是当前 API Server 内该房间有效连接数。同一账号两个标签页为两个连接；一个标签页关闭后只减一。连接注册成功后增加，统一清理入口仅成功移除一次，拒绝握手不计入。

V1 **不建立 room_members 表**。原稿没有历史访问审计或长期成员关系需求，持久表容易与实时连接混用。当前连接由 RoomHub 持有，进程重启后归零并等待客户端重连。将来需要访问历史时另行设计会话记录及其保留期，不复用在线计数。

## 计数与历史

like_count 是指定 session_id 内唯一有效 LIKE_CLICKED 事件的累计数。Redis 保存各场次独立的实时投影，MySQL 的互动事件是持久化核对依据。计数未知时返回不可用状态，不将缺失键当作零展示。

历史查询只包含已持久化弹幕，允许相对实时消息滞后。前端用 event_id 合并，不能将历史记录再次显示为一次新的实时发送。点赞历史不提供用户列表接口；V1 不建立 room_stats 汇总表。
