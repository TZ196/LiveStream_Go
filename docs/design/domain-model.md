# LiveStream 领域模型与业务规则

基线 V1.1。负责业务口径与状态转换。接口字段由 [HTTP](api-spec.md) 和 [WebSocket](websocket-protocol.md) 定义，物理存储由 [数据设计](database.md) 定义。

这份文档先回答“房间、场次和用户各是什么”，再解释谁能操作。阅读实现时，可先看 [房间 Service](../../backend/internal/room/service.go) 的 `Create`、`Close`、`Reopen`，再看 [Repository](../../backend/internal/room/repository.go) 的事务；登录与密码规则在 [用户 Service](../../backend/internal/user/service.go) 和 [password.go](../../backend/internal/user/password.go)。

## 对象及关系

User 表示注册账号；Room 表示由一个用户创建的长期互动房间；LiveSession 表示该房间一次独立开播场次；Connection 表示一次已认证且已注册到某一场次的连接；Danmaku 表示一次文本发送事件；LikeClick 表示一次物理点击，一个点赞事件携带同一用户在同一场次的一个批次。场次由 live_sessions 记录。

一个用户可以拥有多个房间，并在连接上限内同时打开多个页面。一条连接只属于一个房间、一个场次和一个用户；场次在握手或准入时绑定，不能因房间重开自动切换。关闭浏览器页面仅结束该连接，不关闭房间。

## 权限

| 行为 | 访客 | 已登录用户 | 当前房主 |
| --- | --- | --- | --- |
| 注册、登录 | 允许 | 允许 | 允许 |
| 查看房间及历史 | 拒绝 | 允许 | 允许 |
| 创建房间 | 拒绝 | 允许 | 允许 |
| 进入开放房间、弹幕、点赞 | 拒绝 | 允许 | 允许 |
| 结束直播、重新开播该房间 | 拒绝 | 拒绝 | 允许 |

客户端不得指定业务 user_id 或 owner_id。服务端从认证上下文确定操作者。V1 不提供用户改名、账号删除和房间删除接口。

## 用户及输入口径

- 用户名去除首尾 ASCII 空格后转为小写，使用 3 至 32 位 ASCII 字母、数字或下划线，首位为字母；规范化值唯一。
- 密码为 12 至 128 个 Unicode 字符、最多 512 个 UTF-8 字节，不自动去空格或截断。
- 房间标题去除首尾空白后为 1 至 80 个 Unicode 字符。
- 弹幕为 1 至 200 个 Unicode 码点，不能全部为空白；保留合法文本原样，不执行 HTML。大小限制和合法控制字符见 WebSocket 协议。发布前以只读 AC 自动机审核规范化副本；命中当前人工词库则拒绝，词库不构成完整语义审核。每用户在每个房间独立使用 10 秒/10 个新请求的滑动窗口；同账号同房间的多页面共享额度，重新开播不重置尚未过期的窗口。相同请求重试不重复限流，首次审核拒绝也计一次。请求身份仍按用户与 request_id 核对，不能换房间复用同一个 ID。
- 本场点赞榜按用户累计点击数降序，同分按数值用户 ID 升序，每个名次只占一个位置。只展示有点赞的前 100 人。用户离开后保留成绩，在榜用户看到自己的行被标出，榜外用户只看到自己的点击数。未点赞时个人数为 0。每次重新开播使用新的榜单。
- 点赞为连续点击计数，同一用户可以多次点赞。500 毫秒内的点击可共用一次请求及确认，批次中的每一下都计入总数。它不表示“一人一票”，V1 不提供取消点赞。

## 房间状态

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| 不存在 | 合法用户创建 | OPEN，设置 owner_id 和 created_at，并创建首个独立场次 |
| OPEN | 房主结束直播 | CLOSED，设置本轮 closed_at，并结束当前场次 |
| CLOSED | 房主再次关闭 | 返回当前 CLOSED，不改写 closed_at |
| CLOSED | 房主重新开播 | OPEN，closed_at 清空，沿用原房间编号、所有者、标题和创建时间，并创建新的 session_id |
| OPEN | 房主再次开播 | 返回当前 OPEN，不重复创建房间 |
| CLOSED | 申请加入或新的弹幕、点赞 | 拒绝 ROOM_CLOSED |
| 任意已存在状态 | 非房主关闭或重新开播 | 拒绝 FORBIDDEN，不修改状态 |

OPEN 在页面显示为“直播中”，CLOSED 显示为“已结束”。结束的是本轮直播，房间本身长期保留；房主下次使用原房间重新开播，无需再创建。当前开播仅改变互动房间状态，不包含音视频推流。

关闭或重开不删除已接受事件及历史数据。每次从 CLOSED 转为 OPEN 都创建独立 session_id；点赞按 session_id 分别计数和持久化，重新开播不混入上一场。房间累计数若有需求可另行明确，不代替单场统计。房间状态来自 MySQL，RoomHub 中的状态只用于当前进程快速准入和连接管理。房间事务先锁定房间行，再同时更新房间和场次。同方向重试沿用已有场次，交错反向操作按锁内执行顺序改变状态。

## 关闭与在途请求

Room Service 与消息准入共用进程内的房间准入锁。关闭请求在锁内完成权限检查和数据库状态更新，再将本地房间标为关闭；数据库更新失败时保留原开放状态。Kafka 发布及 WebSocket 网络写入不在房间锁中等待。

通过准入检查并开始发布的操作属于在途操作，即使 Kafka 确认晚于关闭，仍可接受并持久化。关闭后不接受新操作。点赞没有发布前请求记录；弹幕已有 Redis 冻结记录和 SQL 最终结果查询。已接受弹幕可核对原 ACK；原场结束且发布结果未确认时保留未确认并通过历史核对，不重新发布至新场。旧场点赞安全查询及完整在途完成屏障仍须后续设计。

RoomHub 在关闭后拒绝新注册并关闭已有连接；当前不保证发送专用关闭通知，前端通过重新查询房间状态识别关闭。实时消费者对关闭场次的迟到事件仍更新该原场次的幂等记录和统计，但不再发送至已结束场次或后续场次的业务广播。点赞可能分布于多个分区：关闭本身只阻止新准入，不表示已准入点赞已全部持久化。若未来要求最终完成确认，不能只在一个分区写结束标记；必须先停止新准入，处理所有已准入发布者及结果未知的请求，再建立并核对覆盖所有相关分区的持久化屏障。无法确认旧发布者停止或在途结果时保持未完成；该屏障尚待单独设计和实现。

点赞批次、待推送快照和连接都绑定 session_id。新开场次单独计数，旧场的未确认批次不会发往新场。关闭时在途发布的最终核对仍属 TODO-01。

## 在线连接及成员记录

在线连接数是后续目标，定义为当前 API Server 内该房间的有效 WebSocket 连接数：同一账号两个标签页算两个连接，一个标签页关闭后只减一。当前已经管理连接注册与移除，但尚未交付该计数及展示，不能把连接管理等同于在线人数已实现。注册和清理见 [audience.go](../../backend/internal/realtime/audience.go)。

V1 **不建立 room_members 表**。原稿没有历史访问审计或长期成员关系需求，持久表容易与实时连接混用。当前连接由 RoomHub 持有，进程重启后归零并等待客户端重连。将来需要访问历史时另行设计会话记录及其保留期，不复用在线计数。

## 计数与历史

like_count 是指定 session_id 内按 event_id 去重后的各 LIKE_CLICKED 事件的点击数之和。旧事件按 1 计。Redis 保存各场次独立的实时投影，MySQL 的互动事件是持久化核对依据。计数未知时返回不可用状态，不将缺失键当作零展示。

MySQL 历史接口只包含已持久化弹幕，允许相对实时消息滞后；直播页面的最近五分钟查询则读取 Redis 缓存，缓存可能包含尚未落库的已接受事件。两种查询不能当作同一种一致性保证，接口见 [HTTP 契约](api-spec.md#最近弹幕缓存)。前端用 event_id 合并，历史记录不作为新的实时发送。直播中的场次提供公开前 100 名与登录者本人的累计数。已结束场次的点赞明细没有对外查询入口。V1 不建立 room_stats 汇总表。
