# 直播间在线人数与连接替换 · 面试问答

## 1. 你做了什么？为什么用 Redis？

我做了直播间在线人数和同账号连接替换。一个账号只能有一条有效直播连接。新窗口成功入房后，旧窗口退出互动并保留登录。同房间换窗口仍算一人，跨房间则把这一人从旧房间移到新房间。

单 API 用 Go Map 也能做互斥。为了后续扩容，我让 Redis 保存共享归属，让 Go RoomHub 管理实际连接和本机人数。Redis 参与建连、续期和清理，弹幕广播直接走本地连接队列。

## 2. Redis 具体存了什么？

每个账号有一个 `ws:owner:{user_id}` 键，例如 `ws:owner:{1001}`。值是一条 JSON，过期时间设在键上。

| 字段 | 用途 |
| --- | --- |
| `user_id` | 观看记录属于哪个账号 |
| `instance_id` | 连接在哪个 Go API 进程上。进程重启会换编号 |
| `connection_id` | 一条物理 WebSocket 的唯一编号。每次重连都换编号 |
| `room_id`、`session_id` | 房间编号和本次直播场次编号。同一房间重新开播会换场次 |
| `watch_id` | 一次观看的编号。主动进入生成新编号，普通重连沿用原编号 |
| `generation` | 归属代次。键存续期间随新连接登记递增，键重建时可能从 1 开始 |
| `run_id` | Redis 进程的运行编号，用来识别 Redis 重启后恢复出的旧登记 |
| `active` | 这条归属是否登记为活跃。正常断开后可短期保留观看记录，此时为 `false` |

## 3. 新窗口在哪一步接管旧窗口？

1. 前端用登录凭证申请一次性票据。后端校验票据、来源和场次，预留连接名额，再完成 WebSocket 升级。
2. HTTP 101 代表协议升级完成。后端再核对场次仍然开放，执行 Redis 归属登记。
3. Redis 确认后，RoomHub 在一次本地更新中停用并摘除旧连接、加入新连接。新窗口收到 `ROOM_STATE` 首屏后才开放互动。

旧连接从本地停用时起就不能接收新的互动请求。已通过准入的点赞、弹幕仍按原请求和原场次处理。

## 4. 三个 Lua 脚本各做什么？旧连接为什么清理不到新记录？

- `claim_owner.lua` 原子校验预期归属、写入新连接、递增代次并设置过期时间。
- `renew_owner.lua` 核对 Redis 运行编号、API 实例、连接编号、代次和 `active`，匹配才延长租约。
- `release_owner.lua` 用相同条件确认归属，再把 `active` 改为 `false` 并保留 30 秒供正常重连。Go 清理人数时也确认被移除的是当前连接。

比如旧连接是 `C1`，代次为 `1`。键过期重建后，新连接 `C2` 的代次也可能为 `1`。Lua 还会比较连接编号，`C1` 的迟到清理因此不会动到 `C2`。

## 5. 新窗口失败时，旧窗口还能看吗？

如果握手失败或登记前的场次校验没通过，Redis 归属还没改，旧窗口可以继续。写 Redis 超时则可能已经成功，后端会用本次生成的 `connection_id` 回查。只有确认有效归属确实属于这条连接，才让它入房。结果无法确认时关闭尚未入房的新连接，避免用另一次写入重复接管。

如果 Redis 已确认登记，但新窗口漏收首屏，可以用原 `watch_id` 尝试恢复。这时旧窗口的状态以当前归属为准。

## 6. 旧窗口没收到关闭通知，为什么抢不回来？

主动进入用 `enter`，取得新的观看编号。自动重连用 `resume`，只能恢复原账号、原房间和原场次的观看。服务端在签票和最终登记时都检查归属。旧窗口的观看编号一旦被换掉，即使没有收到替换关闭码，重连也会被拒绝。页面保留登录，用户可以主动点击「重新进入」。

迟到的主动进入票据也有检查。比如 B、C 的票据签发时都看到 A 正在观看，B 先登记生效。C 用先前的票据握手时，Redis 发现当前归属已从 A 变成 B，就拒绝该票据。

## 7. Redis 暂停或重启时，已有连接怎么办？

租约是 30 秒，后台每 10 秒校验并尝试续期。Redis 不可用时拒绝新登记，已有连接最多使用最后一次确认的剩余租期。检查确认归属变化或本地租约到期后，旧连接停用。Redis 重启后，AOF 即使恢复出原值，旧记录的 `run_id` 也无法通过新进程的校验。

Ping/Pong 检测 WebSocket 的网络连接，续租确认它仍拥有观看资格。连接在租期内继续保留时，点赞和弹幕能否发送仍由各自的依赖状态决定。

## 8. 在线人数、连接配额和多 API 有什么边界？

人数只算当前场次已有效入房的账号。`ROOM_STATE` 给出首屏人数，`ROOM_ONLINE_UPDATE` 按秒合并变化，客户端根据场次、实例和人数版本过滤迟到帧。房间统计接口读取同一份本地人数。

握手中和退出中的连接也占资源。同房换窗口可以一直显示一人，切换期间却占用两个连接名额。单 API 默认 256 条是保护阈值。同账号最多一个并发握手，每个对齐的 10 秒窗口最多申请六次票据。

当前按单 API 验收。跨节点时 Redis Pub/Sub 可以通知旧 API 关闭指定连接，通知遗漏由续租校验兜底。多 API 上线还要处理共享票据、跨节点业务广播、全局人数和严格的接管顺序。

**怎么验证的？** 实际跑过浏览器双窗口、跨房切换、迟到票据和旧连接清理，也暂停并重启过隔离 Redis，确认 AOF 恢复出的旧归属无法续期。[验证报告](verification/reports/ws-presence.md)
