# LiveStream 开发计划

基线 V1.1。D0、P1a、P1b 账号流程和 P2 房间管理已实现。计划遵循需求明确、设计可核对、按阶段实现、验证后记录结果的流程；实际验证和未覆盖项见项目状态。

API 负责用户、房间、连接与实时消费；Worker 负责持久化；前端按协议实现用户操作和状态展示。配置、部署与验证随相应阶段交付。

## 阶段计划

| 阶段 | 工作及交付物 | 必要依赖 | 退出条件 |

| P1a 工程骨架 | backend Module、Hertz、配置日志、健康接口；Vue/TS/Vite 页面与 HTTP 封装 | Go、Node | 前端调用健康接口，后端构建与前端类型检查通过 |

| P5 弹幕事件接入与链路加固 | 将弹幕接入 Kafka，验证同场弹幕顺序、分区分配、重试与关闭边界 | P4 | Broker 确认、分区顺序及消费者重试均通过对应故障测试 |
| P6 历史与恢复 | 弹幕历史查询、异常隔离、投影恢复与跨分区故障演练；扩展已在 P4 引入的 Worker | P5 | 重启、重复、数据库故障、Redis 丢失、隔离修复案例通过 |
| P7 容器交付 | 后端镜像、前端构建同源托管、完整 Compose 和运行说明 | P6 | 五服务可重复启动，前端可访问，数据卷重启保留，内外 Kafka 地址正确 |

P2 的“进入页面”仅为导航；真正的加入、退出及在线连接数在 P3 交付。Worker 随 P4 点赞持久化创建；P6 在已有 Worker 基础上补充历史和完整恢复能力。依赖和检查随阶段建立，不为形式完整创建空服务。

## 点赞优先的近期安排

当前已交付场次模型及点赞链路子集；Redis 和 MySQL 分别由独立消费组处理。固定房间每次开播拥有独立场次。点赞已补正常重启核验与一次性重建；弹幕、完整连接协议和异常隔离仍按后续阶段完成。

关闭与在途发送、断线清理见 [待解决问题](status.md#待解决问题)。P2 只交付数据库房间状态与权限；重开后的旧连接清理和迟到消息边界随实时实现验收。

## 各阶段消息承诺

| 阶段 | 弹幕接受边界 | 点赞接受边界 | 历史与恢复 |
| --- | --- | --- | --- |
| P3 | 入本进程有界分发队列，ACK accepted_via=memory | 不启用 | 仅内存演示；不承诺历史持久化 |
| P4 | P3 弹幕链路仍独立 | Kafka Broker 确认后 ACK accepted_via=kafka；Redis 与 MySQL 消费组独立处理 | MySQL event_id 唯一，事务成功后提交对应 offset；点赞单 API 重建已实现，其他历史与异常隔离待后续 |
| P5 | Kafka Broker 确认后 accepted_via=kafka | 同 P4 | 扩展弹幕事件链路及故障验证 |
| P6 起 | 同 P5 | 同 P4 | 历史查询、异常隔离和受控投影恢复 |

点赞第一次交付就以 Kafka 接受为准，不实现旧计划的 Redis 直接计数路径，也不将 Producer 直接 +1 与 Kafka 消费 +1 并行运行。发布 Kafka 前不登记请求指纹，也不依赖 Redis；重复事件由消费者去重。相同 ID 的不同内容可能同时进入 Kafka，消费者发现冲突后暂停并告警。事件时间取自客户端 UUIDv7 request_id，不声称是首次服务端时间；重试保持原请求。不可确定结果的长期后台处理须在交付前确定，不得把等待结果作为成功或确定失败，也不向前端展示 Kafka 内部故障细节。

P3 内存弹幕仅用于该阶段演示；P5 切换前停写并停止旧进程。已有内存演示数据不自动成为 Kafka 历史，若要保留须先设计迁移；不得擅自清理数据。P4 的 Redis 投影发生丢失时暂停写入；仅当日志覆盖全部所需事件且可证明完整重建时恢复，本轮点赞恢复不代表 P6 的弹幕历史、异常隔离或恢复中断续建已交付。

## 每阶段工作流程

1. 从更新后的 main 建立任务分支，检查已有修改，阅读本阶段需求、契约和相关 REF/ISSUE。
2. 明确范围、模块、数据影响与验收条件；重要选择和失败边界直接维护在对应设计中。
3. 完成实现和适用检查，区分通过、失败、未运行；验证要求见 [验证计划](verification/plan.md)。
4. 在验证报告记录环境、代码提交、命令、结果及限制，项目状态只更新当前摘要和待解决事项。
5. 审查 Diff 后提交并推送任务分支，创建指向 main 的 PR。满足仓库要求后，仍须等待用户明确同意本次合并，才执行合并和本地主干同步。
6. 删除任何本地或远程任务分支前，也须获得用户本次明确同意；询问“能删除吗”只进行检查和回答，批准合并不自动包含删除。未获同意时保留任务分支。部署另按已有授权执行。

P4/P5 接入前锁定 Redis/Kafka 客户端和镜像版本，测量 Redis 键与内存预算；P4 在新建点赞 Topic 前确认分区数与热点验收，保留 16 分区作为当前设计基线；环境状态以实际检查为准。保持模块化单体，后续扩展以需求和测量依据驱动。

## 当前点赞子链路实现边界

已接通固定房间下的独立场次、一次性票据、WebSocket 点赞、Kafka Producer、Redis 实时消费和 MySQL Worker。现有实现覆盖点赞子集；P3 弹幕、在线人数、完整 WebSocket 协议和 P6 投影重建尚未交付，不能将整个 P3/P4 验收视为完成。点赞已接入前端 500 毫秒聚合、200 毫秒同场快照和每组默认 4 个成员。此前的 Redis 故障和 Worker 积压见 [点赞链路报告](verification/reports/likes-chain.md)。

## 弹幕与 AC 审核的实施顺序

已确认独立 live.danmaku、两个弹幕消费组和 room_id:user_id 分区键。本轮以 main 合并点赞恢复后的提交 c800921 为依赖基线，保留迁移 1–6，新增迁移 7。当前任务分支 feat/danmaku-ac；分阶段提交和检查，未完成全链路验收前不视为交付。

1. 基础：配置、隔离 Topic、冻结事件、词库及只读 AC；不运行会跳过真实消息的空消费者。
2. 准入：Redis 原子请求状态、滑动窗口、审核版本冻结和 Broker 确认；补并发、重试、结果未确认验证。
3. 后端闭环：共享连接生命周期解耦、场次有界分发、独立实时组、弹幕事务及检查点。
4. 前端和历史：一条房间连接、独立业务状态、有界发送队列、原请求重试和历史去重。
5. 联调：真实隔离中间件、进程故障、点赞恢复回归及分开测量服务端入队与浏览器接收延迟。

词库为 backend/configs/moderation_words.tsv 的 80 条人工种子词，非完整语义审核。请求账本依赖 Redis；原冻结记录和持久化历史均不可得时保持未确认，不用新审核版本重造旧事件，不建设 Outbox 或复杂请求恢复任务。
