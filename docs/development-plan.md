# LiveStream 开发计划

基线 V1.1。D0、P1a、P1b 账号流程和 P2 房间管理已实现。计划遵循需求明确、设计可核对、按阶段实现、验证后记录结果的流程；实际验证和未覆盖项见项目状态。

API 负责用户、房间、连接与实时消费；Worker 负责持久化；前端按协议实现用户操作和状态展示。配置、部署与验证随相应阶段交付。

## 阶段计划

| 阶段 | 工作及交付物 | 必要依赖 | 退出条件 |
| --- | --- | --- | --- |
| D0 需求与设计 | 统一需求、领域、契约、数据、可靠性与追踪矩阵 | 现有资料 | 重大冲突有明确选择，文档链接和示例可校验 |
| P1a 工程骨架 | backend Module、Hertz、配置日志、健康接口；Vue/TS/Vite 页面与 HTTP 封装 | Go、Node | 前端调用健康接口，后端构建与前端类型检查通过 |
| P1b 用户认证 | MySQL Compose、用户 Migration、密码与 JWT、注册登录页 | Docker/Compose、MySQL | 注册登录、用户名冲突、错误密码、过期令牌和权限案例通过 |
| P2 直播间 | 房间 Migration、所有者权限、列表详情、结束直播和重新开播；前端页面导航 | P1b | 开关播权限、同方向幂等、交错状态一致，重开保留原房间 |
| P3 实时弹幕 | 一次性票据、WS、RoomHub、连接心跳与清理、memory 发布器 | P2 | 多浏览器互通、房间隔离、关闭竞态、慢客户端及断连验证 |
| P4 Redis 互动 | 点赞、业务限流、请求记录与直接模式原子更新 | P3、Redis | 同请求并发不多算、窗口和队列边界可验证 |
| P5 Kafka 链路 | 固定事件、Producer、API 实时消费者、kafka 发布器 | P4、Kafka | Broker 确认后 ACK，丢失 ACK 重试不多算，发布结果未知可解释 |
| P6 可靠持久化 | Worker 入口、事件表、inbox/checkpoint、历史查询、异常隔离与投影恢复 | P5 | 重启、重复、数据库故障、Redis 丢失、隔离修复案例通过 |
| P7 容器交付 | 后端镜像、前端构建同源托管、完整 Compose 和运行说明 | P6 | 五服务可重复启动，前端可访问，数据卷重启保留，内外 Kafka 地址正确 |
| P8 测量与报告 | 逐级负载和故障压测、报告及瓶颈分析 | P7 | 报告包含硬件、参数、分位延迟、积压及错误，能够复现 |

P2 的“进入页面”仅为导航；真正的加入、退出及在线连接数在 P3 交付。Worker 到 P6 才创建。依赖和检查随阶段建立，不为形式完整创建空服务。

## 点赞优先的近期安排

当前 P2 已完成。下一步以点赞为目标，先接通 P3 的票据、WebSocket 和 RoomHub，再完成 P4 的 Redis 原子去重计数与状态推送。完整弹幕功能继续按 P3 验收跟踪；P5/P6 的 Kafka、持久化职责和既定协议保持不变。

关闭与在途发送、断线清理见 [待解决问题](status.md#待解决问题)。P2 只交付数据库房间状态与权限；重开后的旧连接清理和迟到消息边界随实时实现验收。

## 各阶段消息承诺

| 阶段 | 弹幕接受边界 | 点赞接受边界 | 历史与恢复 |
| --- | --- | --- | --- |
| P3 | 入本进程有界分发队列，ACK accepted_via=memory | 不启用 | 请求记录在内存，仅同一进程生存期内去重；无历史持久化承诺 |
| P4 | 同 P3，request 记录改由 Redis 管理 | Redis 中原子完成请求接受、去重、计数，accepted_via=redis | 缓存保持期间可核对；尚无全历史恢复能力 |
| P5 | Broker 确认后 accepted_via=kafka | 同左，计数仅由实时消费者更新 | 有日志但尚无完整 Worker 与恢复；不声称历史功能完成 |
| P6 起 | 同 P5 | 同 P5 | 至少一次消费、业务去重、MySQL 历史及停写恢复 |

P3/P4 弹幕的崩溃窗口可能丢失或重复即时广播，客户端按 event_id 去重；不能把 memory ACK 解释为持久化。P4 LIKE 的计数和接受记录必须在同一脚本更新，避免计数已加而请求仍显示未接受。

首次进入 P4 时显式初始化直接模式的投影 epoch 和已有房间零值；此时尚无历史点赞。之后投影丢失不得再次伪装为首次初始化。直接模式的 meta 不含 Kafka 位移，分区进度键从 P5 建立；P4 丢失数据时先停写，再依据备份或单独的数据处置决定恢复。

从直接模式切到 Kafka 模式时停写并停止旧进程，不允许新旧发布路径并行。P3/P4 的开发数据不自动成为 Kafka 历史；需要保留时必须先设计迁移，不能把旧计数与新日志直接相加。任何清空开发数据的操作另外取得明确授权。

P5 期间发生 Redis 丢失时暂停写入；只有日志覆盖全部开发事件且能完整重建时才恢复，不能套用尚不存在的 P6 数据库恢复能力。

## 每阶段工作流程

1. 从更新后的 main 建立任务分支，检查已有修改，阅读本阶段需求、契约和相关 REF/ISSUE。
2. 明确范围、模块、数据影响与验收条件；重要选择和失败边界直接维护在对应设计中。
3. 完成实现和适用检查，区分通过、失败、未运行；验证要求见 [验证计划](verification/plan.md)。
4. 在验证报告记录环境、代码提交、命令、结果及限制，项目状态只更新当前摘要和待解决事项。
5. 审查 Diff 后提交并推送任务分支，创建指向 main 的 PR。满足仓库要求后，仍须等待用户明确同意本次合并，才执行合并和本地主干同步。
6. 删除任何本地或远程任务分支前，也须获得用户本次明确同意；询问“能删除吗”只进行检查和回答，批准合并不自动包含删除。未获同意时保留任务分支。部署另按已有授权执行。

P4/P5 接入前锁定 Redis/Kafka 客户端和镜像版本，测量 Redis 键与内存预算；环境状态以实际检查为准。保持模块化单体，后续扩展以需求和测量依据驱动。
