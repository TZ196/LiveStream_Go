# 第六步：创建、查看和关闭直播间

日期：2026 年 11 月 21 日。本轮实现 P2，为后续点赞提供真实 room_id、房主身份和开放状态。沿用认证、Hertz 和 GORM，新增房间表的第 3 版迁移；没有新增依赖。关闭与在途发送、断线清理已列入 [待解决问题](../status.md#待解决问题)，本轮不把这些实时能力算作完成。

## 操作流程

按 [README](../../README.md) 启动 MySQL，先执行 `go run ./cmd/migrate`，再启动 API 和前端。已有版本 2 的数据库只新增 live_rooms 和成功记录 3，用户数据与版本 1、2 的成功时间保留。

1. 注册并登录，默认进入“直播间”。“我的账号”仍可查看账号和退出。
2. 输入标题创建房间，成功后进入详情；列表支持开放/关闭、全部/我的房间筛选和“加载更多”。
3. 用另一个账号登录，可以查看房间，但不能关闭他人的房间。后端也检查权限，隐藏按钮不能替代鉴权。
4. 房主点击“关闭房间”，确认后状态变为已关闭；关闭后的详情仍可查看，不能重开。

本阶段的房间详情是 HTTP 页面；进入详情还没有建立实时连接，也不增加在线计数。点赞与弹幕尚不可用，页面不展示虚构计数。

## 场景一：房主重复点击关闭

场景是两个页面同时关闭一个房间。单纯“先查 OPEN，再无条件 UPDATE”会让后到的请求覆盖 closed_at。

Service 先确认房间存在及所有者；Repository 更新时再次要求 id、owner_id 和 status=OPEN 同时匹配，原子设置 CLOSED 和 closed_at，然后读取最终状态。只有第一个成功更新的请求写入关闭时间，其余读取同一个结果。非房主即使对已关闭房间请求关闭，仍返回 403。

这里依赖 V1 不转移所有者、不删除房间、不重开，状态只向前变化，因此不额外建立事务或进程锁。数据库条件更新解决的是持久状态重复写；接入 WebSocket 后，仍需按领域规则补齐内存连接与在途操作协调，不能据此宣布 TODO-01 已解决。

故障时返回 503，不伪报关闭成功；数据库写入可能已生效而响应丢失，页面提示刷新状态确认。40 次并发关闭与真实数据库锁等待验证记录见 [项目状态](../status.md)。

## 场景二：翻页时新增房间

列表按 id 倒序，下一页读取 id 小于上页最后一条的记录；多取一条判断是否有下一页。与 offset 分页相比，新插入的房间不会把已看过的记录挤到下一页，代价是不能直接跳到任意页码，也不返回全表总数。

游标保存最后 ID、状态和实际所有者筛选；owner=me 绑定当前用户，切换状态或账号不能复用原游标。游标只是分页边界，不是权限凭证，数据库仍独立应用认证后的筛选条件。房间可能在翻页期间关闭，这不是跨请求的数据库快照；刷新列表可获取最新状态。

## 迁移与失败处理

版本 3 只新增表，不改写已经成功的版本 1、2，也不在 API 启动时改表。live_rooms.owner_id 外键限制为 RESTRICT，状态与关闭时间使用 CHECK。启动及 readyz 只读检查结构版本 3 和所需列，stage 为 P2。

DDL 失败时停止，不写成功记录；若建表已成功但登记失败，先核对表、约束与记录，再受控修复。没有自动删表回滚；出现需修改结构的问题，使用新的迁移前向修复。旧 API 要求恰好版本 2，升级数据库后应使用本轮 API，不能直接回退旧二进制。

创建房间没有 HTTP 幂等键。页面防止重复提交，但网络失败时仍可能已经创建；先选择“我的房间”刷新确认，不自动重发创建。前端切换筛选会取消旧列表请求，退出页面会释放正在进行的请求。
