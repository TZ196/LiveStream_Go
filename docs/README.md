# LiveStream 文档基线与职责

V1.1 设计基线，2026 年 11 月 18 日。本目录将业务需求、系统设计、实现计划和验证责任分开维护，作为后续逐步实现的依据。当前状态为设计已编制、业务尚未实现。

## 基线及来源

本基线继承 2026 年 11 月 17 日修订稿中的 Hertz、Vue 3、backend 目录、单 API Server 和独立 Worker 方案，补充鉴权、幂等、房间生命周期、故障恢复及验收设计。

旧 Word 工作副本、修订稿及归档目录已按用户要求删除。当前 Markdown 文档是唯一维护中的设计基线，不保留另一套旧方案。

用户后续明确要求优先于既有设计。[工程规则](../AGENTS.md) 管理技术边界与协作行为，下表指定每项设计事实的唯一维护位置。发生冲突时先对照决策记录并同步修正相关文档，不通过混用旧稿解决冲突。

## 阅读与交付顺序

1. 阅读需求规格和领域模型，确认范围与业务语言。
2. 阅读架构，理解 API、Worker、前端和基础设施的分工。
3. 按当前阶段阅读接口、协议、数据及可靠性设计。
4. 对照开发计划和验证矩阵实施，按项目讲解要求保留场景与证据，完成后将真实结果写入项目状态。

设计参数是 V1.1 的默认约定；依赖补丁版本、硬件容量和性能结果在实施阶段实测并锁定。改变业务范围或协议时同步需求、相关契约和验证矩阵；改变主要设计选择时新增决策记录。

## 本轮审查问题落点

| 审查问题 | 设计处理 | 验证位置 |
| --- | --- | --- |
| 两个 Word 版本与工程规则不一致 | 当前 Markdown 基线统一，旧 Word 与归档删除 | DOC-01 |
| 重试产生新事件导致重复处理 | 有界请求窗口、稳定事件标识、请求指纹和接收状态 | IDEM-01 至 IDEM-04 |
| 浏览器 WebSocket JWT 传递未定义 | Bearer HTTP 换取短时一次性房间票据 | WS-01、WS-02 |
| Redis 计数丢失或重放重复累计 | 原子去重、保留窗口、暂停写入后的全量恢复 | REC-01 至 REC-03 |
| 成员表与在线连接概念混淆 | V1 使用连接状态，不建立 room_members 表 | ROOM-02、ROOM-03 |
| 消费失败统一进入死信 | 区分可恢复依赖故障与异常事件，持久隔离后再推进 | KAFKA-01 至 KAFKA-04 |

以上编号的完整步骤见 [验证与需求追踪](verification.md)。设计闭环不等于运行验证已经通过。
